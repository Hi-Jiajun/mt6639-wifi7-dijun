# MT6639：6GHz 真实关联与 320MHz 初步验证

日期：2026-10-22。对象：小米 15S Pro / dijun / MT6639；AP：XR1710G / MT7996。

## 1. 结果与边界

本机已完成独立 6GHz SSID 上的 WPA3-SAE 关联和局域网双向 ICMP 收发。手机与 AP 对应客户端均报告实际工作带宽 320MHz；不是只看 capability、AP 配置或 Wi-Fi 7 图标。

- 频率 6135MHz / 信道 37，手机 supplicant 在收发前后均为 `COMPLETED`、`key_mgmt=SAE`、`pmf=2`。
- 手机 `iw link` 的 RX 速率为 5764.8Mbit/s、320MHz；这个数字是 PHY 速率，不是实测吞吐。
- AP 对应同一手机 MAC 的 station 条目为 authorized/associated，TX/RX 速率均带 `320MHz EHT-MCS ... EHT-NSS 2`。
- 指定 `wlan0` 到 AP 管理地址的 ping 为 10 发 10 收、0% 丢包、无重复包；收发前后的 BSSID、手机 MAC、IP 和频率一致。
- 本次独立 SSID 不证明 MLO。MLO、吞吐、长期稳定性、功率/频谱/全信道射频验证仍未完成。

这推翻了早先“wiphy 没有 6GHz，所以整机一定没有 6GHz 射频”的推断。现在至少能证明本机这套硬件/固件在这个信道上可实际接收、关联和收发；不能外推为全部频率、全部功率模式或所有芯片宣传功能均已验证。

## 2. 实现路径

沿用已经独立验证的最小配置路线：

1. 对本次 boot、内核版本及原厂 ko/cfg 校验，手机和 Mac 双份备份一致。
2. 仅临时 bind 覆盖 `DisallowBand6G 1 → 0` 的配置；通过原厂接口设置测试国家码变量 US。
3. 正常关闭/开启 Wi-Fi，使原厂驱动重建并接收国家码，而不是卸载驱动或 PCI rebind。
4. 核对 GET_WIPHY 的 60 项 6GHz 频率 `disabled=0/no_ir=0`，扫描并连接 AP。
5. 自动解除 bind、恢复 CN/清除 override/恢复扫描设置并正常重建，复核原厂文件和 5GHz 连通。

未刷分区、未改 efuse/校准、未加载新 WLAN LKM、未改 stock WLAN ko；本轮只恢复使用已有 root-only 入口，未修改 root 链，也未加载 KernelSU。已有 root 链本身的收尾辅助模块不属于新 WLAN 模块。

## 4. 保存网络变化与回滚口径

assoc 的基线只有三个 Android 保存网络。测试过程中增加了 ID3 的独立 6GHz 测试 SSID；该项不是实验脚本通过 `add-network`/`connect-network` 创建的，脚本也没有读取或写入密码。本窗口曾通过设置界面点击网络，期间 UI 列表有重排/并发变化，因此不能将新增项归因到一个已完全隔离的自动步骤。

为保护用户或其它任务的改动，没有删除该项。严格列表比较真实地报了 `rollback_ok=0`，不能将它改写成“全部回滚通过”。独立检查确认：

- cfg/ko 为原厂 SHA，国家码 CN，override=null，扫描常开值为 1。
- GET_WIPHY 与本轮 baseline 逐字一致；探针和 trace instance 列表前后相同。
- 5GHz WPA3 重新连接，恢复 ping 10/10、无重复包。
- 保存网络只新增这一个测试配置，原有项未移除。

离线验证器只有在显式指定预期的这一项增量时才接受该轮，并输出 `strict_rollback=false`，不会静默放宽断言。后续 assoc2 以包含该保存网络的现状重新备份和比较。

## 5. 仍需追查

1. AP 首次有效快照有较多 TX retries/failed；计数增长原因、驱动统计口径和持续业务表现未确定。ICMP 10/10 不能抵消这一风险，也不足以宣称日用稳定。
   assoc2 的 seq6 出现 6 个重复回包，独立业务验证器按设计拒绝通过，未放宽无重复断言。随后先测原厂 5GHz 到同一个 AP 管理地址：10/10 无重复；AP 的 Ethernet 抓包也是每序号一请求一回复。继续在 6GHz 同时抓手机 wlan0 与 AP 的独立 6GHz AP 接口，仅过滤这两个端点的 ICMP，不抓其它业务，不改 AP 配置。
2. 定向 `iw scan freq 6135 passive` 返回包含其它频率的 BSS 缓存，不能把全部输出当成本次扫描新收到的帧，也不能据此断言全程只有被动扫描。framework 新出现的 6135 记录、真实关联及 AP 客户端证据才是本轮更强证据。
3. 手机某些 `mlo_status` 接口返回 FAIL；独立单链路连接不能证明 MLO 不支持，也不能证明 MLO 已开启。
4. 320MHz 初步链路验收已达成；LAN 实际吞吐、上下行大流量、温升/休眠/漫游及重复启动回归另测。
5. 旧 `mt6639-full` 模块的 apply/reload 含历史驱动卸载路径，仍不可用于当前方案；新验证成果不等于旧模块可以日用。
