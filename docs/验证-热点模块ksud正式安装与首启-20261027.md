# 验证：热点模块经 ksud 正式安装后的首次开机（2026-10-27）

## 背景

此前 mt6639-hotspot 一直是"手工同步 live 目录 + `sha256sum -c`"，没有走 KernelSU 的
正式安装链。本轮把 v0.2.14 用 `ksud module install` 装进 `modules_update`，再重启验证
更新是否被正确应用、以及应用后功能是否退化。

## 安装（重启前）

```text
adb push release/artifacts/mt6639-hotspot-v0.2.14.zip /data/local/tmp/
sha256sum -> 35b0c18204d1708531749489c89e4428f4af32fda31215363c0d8393770da7d9
su -c 'ksud module install /data/local/tmp/mt6639-hotspot-v0.2.14.zip'
  -> Module installed successfully!
暂存目录 /data/adb/modules_update/mt6639-hotspot:
  module.prop: version=v0.2.14 versionCode=22
  sha256sum -c SHA256SUMS -> rc=0
  action.sh / bin/control.sh -> 0755（customize.sh 生效）
```

## 重启与非 root 阶段观测

```text
boot_id     <UUID> -> <UUID>
sys.boot_completed=1
getenforce   Enforcing
id           uid=2000(shell)              <- 临时 root 不跨 boot，符合预期
/data/adb/modules_update/  为空           <- 暂存的更新已在开机时应用
```

**一个操作性事实**：这次开机后 Shizuku 没在跑（`ps -A | grep shizuku` 无输出、
`dumpsys activity services moe.shizuku.privileged.api` 为 `(nothing)`），
而且 `/storage/emulated/0/Android/data/moe.shizuku.privileged.api/` 不存在，
所以主机侧 `sh …/start.sh` 这条路不可用——本 boot 的 root 只能走
Shizuku「通过无线调试启动」+ oneclick App「一键提权」。本轮由 root 会话完成，
轮询到 `su -c id` 返回 `uid=0(root) … context=u:r:ksu:s0`。

```text
/data/adb/modules/mt6639-hotspot/module.prop : version=v0.2.14 versionCode=22

/data/adb/mt6639-hotspot/bridge/lifecycle.lock : 开机后新建（worker 由 service.sh 拉起）

```

即：**暂存更新被正确应用，模块脚本权限正确，service.sh 在开机时拉起了 Settings 桥 worker，
运行状态目录与私钥都保留。**

## 应用后的功能复测（cell 模式）

按用户当前需求再跑一次「Wi‑Fi 开着但不连任何网络 + 移动数据」：

```text
准备: cmd wifi start-restricting-auto-join-to-subscription-id 1
      cmd wifi forget-network <LabNet-5G>
      cmd wifi status -> Wifi is not connected
      ip -4 addr      -> inet 203.0.113.184/8 dev wwan3

control.sh start 6g 20
  state=active task=/data/local/tmp/mt6639-native-ap-3f209235-86400-gQyJLw
  upstream.mode=cell   action.rc=0
  profile.final=native_status=matched band=6g frequency_mhz=6135 width_mhz=20 center_index=37
  dumpsys tethering -> mtap0 - TetheredState - lastError = 0
                       Current upstream interface(s): [wwan3]
  iw dev mtap0 info -> ssid MT6639-Native-6g-20, type AP
  ip -4 addr show dev mtap0 -> inet 203.0.113.93/24
  iptables -t nat -> 1 条 -o wwan3 -j MASQUERADE
  ping -I 203.0.113.93 223.5.5.5 -> 2/2 通

control.sh stop
  state=idle restored=1 action_rc=0
  recovery.resources: native_state=stopped_verified interface_state=removed_verified
    driver_state=restored station_state=not_required_cell
    reg_state=restored ip_forward_state=restored
  recovery.rc=0
```

注意 mtap0 这次分到 `203.0.113.93/24` 而不是之前的 `198.18.117.110/24`——Tethering 从
legacy 网段池里换了一个，说明模块没有写死地址，断言按实际读回值走。

收尾：`cmd wifi connect-network LabNet-5G wpa3 <key>` + `stop-restricting-auto-join…`，
STA 回到 LabNet‑5G/5180MHz，`state=idle`，无 `mtap0`，`Enforcing`。

## 结论

- `ksud module install` 这条正式安装链在本机可用，更新能跨重启正确应用。
- 应用后模块权限、Settings 桥 worker、私钥与运行目录都正常。
- 正式安装的 v0.2.14 在无 STA + 蜂窝场景下功能与手工同步阶段一致（`action_rc=0`、
  `recovery.rc=0`、上游 `wwan3`、NAT 与 ping 均通过）。

## 仍未完成

- Settings 桥的点击闭环、5GHz profile、外部 6GHz 客户端关联、IPv6/offload、
  24 小时稳定性与三次 boot 验收仍未做。
- C02 的 11ax 判据仍失败（见 `docs/C02 并发门控记录（未公开）.md`）。
