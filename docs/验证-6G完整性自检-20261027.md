# 6GHz 完整性自检（v0.2.15）

日期：2026-10-27 22:55–23:02。范围：把 v0.2.14 的"软重启看护"扩成"软重启快车道 + 每 60 秒完整性自检"两条入口共用一个判定，并在真机上用"手动把 country 打回 CN"的方式验证自检真的会自己修回来。**仍不是 cold boot 验收**。

## 为什么加自检

v0.2.14 只认 `system_server` 变化。但下面这些情况从模块内部看**完全一样**：`state=active`、`guardian=alive`、6135MHz 却不在——cold boot 后模块刚被 KernelSU 加载、驱动被重载、Wi-Fi 被开关打断、或任何一次 country override 丢失。只盯 `system_server` 会漏掉它们，用户侧表现依旧是"6G 没了"。

## 实现

`bin/softreboot-watch.sh` 现在有两个入口，但只走一个判定函数 `try_refresh`：

- **快车道**：`system_server` pid 变化（soft reboot），先等 `cmd wifi status` 报 `Wifi is enabled`；
- **慢车道**：每 `MT6639_WATCH_CHECK_INTERVAL`（默认 60 秒）跑一次完整性自检，不依赖 `system_server` 是否变化。

两条入口的判定完全相同，且都是 fail-closed：

1. 6135MHz 已经在 → 什么都不做（自检路径连日志都不写，避免刷屏）；
2. 事务不是 `state=active` → 跳过；
3. Wi-Fi 本来关着 → 跳过，绝不代开；
4. 每 kernel boot 连续失败上限 2 次，**成功即清零**（恢复 LSPosed 也会重启 zygote，成功清零才不会把额度吃光）。

看护依旧不建事务、不恢复事务、不拆事务，只调用一次 200 秒上限的 `control.sh refresh`。

## 真机验证（不重启、无人工 refresh）

| 时间 | 动作 | 结果 |
| --- | --- | --- |
| 22:59:26 | 启动 v0.2.15 看护 | `start pid=26298 interval=5s max_attempts=2` |
| 22:59:4x | 人工制造故障：`force-country-code enabled CN` + Wi-Fi 关开 | `iw phy` 里 `(disabled)` 回到 **75**，6GHz 全灭 |
| 23:00:32 | 60 秒自检到点，发现 6135 缺失 | `refresh-6g: rebuilding Wi-Fi target_6135=0` |
| 23:00:53 | 重建完成 | `before=0 after=1`、`RESULT refresh=registered`、`periodic: refresh rc=0 attempt=1/2` |

## 边界

- 自检只能修"注册态"，不能替 root 兜底：cold boot 后的 KernelSU 与模块加载仍依赖 oneclick 提权链，**"开机自动可用"在没有自动提权前仍不成立**。
- 恢复要付一次 Wi-Fi 关开（约 20 秒）代价；故障到恢复最多约 1 分钟。
- 每 boot 连续失败 2 次后停止重试，避免在确实拿不到 6GHz 的环境里反复打断 Wi-Fi。
- 不覆盖其它信道、其它 AP、320MHz 与长时稳定性；F01/F10 的跨 boot 与 24 小时验收仍空缺。
