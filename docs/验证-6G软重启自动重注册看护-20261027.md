# 6GHz 软重启后自动重注册看护（v0.2.14）

日期：2026-10-27 22:00–22:19。范围：在 `mt6639-6g` 里新增软重启看护，并用三次真实 soft reboot 验证它能否把丢失的 6135MHz 注册自动拉回来。**只覆盖 soft reboot**，cold boot 仍由 oneclick 提权 + 模块 service 负责，不能拿这份记录抵扣跨 boot 验收。

## 为什么要做

`ctl.restart zygote`（以及恢复 LSPosed 时的那次重启）会重建 system_server，但 kernel boot id、6GHz 事务、guardian 与 `wifi.cfg` 的 bind 都不变。Android 的 Wi-Fi country override 存在 system_server 内存里，重启后回落到 `ro.boot.wificountrycode`(CN)，于是所有 6GHz 频点重新变回 `(disabled)`，而模块状态仍然是 `state=active`、`guardian=alive`。此前唯一补救是人工跑一次 `control.sh ... refresh`，用户侧表现就是“6G 又没了”。

## 看护做什么、不做什么

新增 `modules/mt6639-6g/bin/softreboot-watch.sh`，由 `service.sh` 在 `control.sh enable` 之前拉起（ksu 域，单实例 `flock` 锁）：

- 每 5 秒读一次 `boot_id` 与 `pidof system_server`，状态写 `/data/adb/mt6639-6g/softreboot-watch/state`，日志写同目录 `watch.log`。
- **boot 变了**：视为 cold boot，只记基线并清零计数，注册交给 `service.sh`，看护不插手。
- **boot 不变、system_server 变了**：判定为 soft reboot。顺序是「先等 Wi-Fi 服务就绪（`cmd wifi status` 出现 `Wifi is enabled`，最多 20×3 秒）→ 再看 6135MHz 是否真的缺失 → 事务是否仍 `state=active` → Wi-Fi 原本是否开启 → runs `control.sh refresh`（200 秒上限）」。
- 明确不做的事：不建事务、不恢复事务、不拆事务；Wi-Fi 本来是关的就绝不代开；6135 已在就直接返回；每 boot 连续失败最多 2 次，成功后清零（因为恢复 LSPosed 也会重启一次 zygote，成功即清零才不会把额度吃光）。

## 实测时间线（同一 kernel boot `3f209235-…`）

| 时间 | 事件 | 结果 |
| --- | --- | --- |
| 22:12:28 | 首启看护，记基线 `ss=22484` | `baseline` |
| 22:12:52 | soft reboot 后检测到 `ss=22484 → 18312` | 立即调 refresh |
| 22:12:53 | refresh 失败 | `FAIL country_baseline_unreadable`，`rc=3` |
| 22:14:07–22:14:28 | 人工 refresh（系统已就绪） | `target_6135_registered before=0 after=1` |
| 22:15:34 | 再来一次 soft reboot，检测 `18312 → 32130` | — |
| 22:15:41 | 就绪后开始重建 | `rebuilding Wi-Fi target_6135=0` |
| 22:16:01 | 完成 | `after=1`、`refresh rc=0 attempt=2/2`、country=US、disabled=5 |
| 22:17:49 | 第三次 soft reboot，检测 `32130 → 13324` | — |
| 22:18:18 | 完成 | `refresh rc=0 attempt=1/2`，`state` 里 `attempts=0`（成功后清零），STA 自动回 `LabNet-5G`/5180 |

22:12:53 那次失败是本轮的真正收获：zygote 刚重启时 `cmd wifi`/settings 还没起来，`refresh-6g.sh` 按设计 fail-closed 报 `country_baseline_unreadable`。看护因此补了“服务就绪等待”，第二次起就再没出现过该失败。

## 边界

- 只证明 soft reboot 自动恢复；**没有**证明 cold boot 后自动可用（cold boot 的 root 与模块加载仍依赖 oneclick 链），也没有证明 6GHz 在其它信道、其它 AP、长时运行下的稳定性。
- 看护不替代 `F10` 的三次 cold boot 与 24 小时混合使用验收；它只是把“soft reboot 后必须人工点一下”这个日常缺陷关掉。
- 本轮三次 soft reboot 都在同一 kernel boot 内，`boot_id` 未变，这是该缺陷成立的前提，不是跨 boot 证据。
