# 分析：MT6639 原厂驱动的 6GHz 门禁与 wlanProbe 生命周期（只读离线）


## 主线程校准（15:14，优先于下方离线初稿）

1. **撤回“一次性/不可正常重入”的结论。** `g_wlanProbing` 在公共出口清零，是并发/重入保护，不是永久单次锁。主线程使用独立 tracefs 实例，先关扫描始终可用，再经 framework 正常关闭/开启 Wi-Fi，两次均实测命中 `wlanFuncOff → wlanRemove → wlanFuncOn → mtk_pci_probe → wlanProbe → wlanProbe+0x5b0`，且两次网络恢复、ping 3/3。普通开关在 scan-always=1 时没命中不能推导为无法重入。旧 PCI unbind/bind 失败的原因仍未证实。
2. **更正字节偏移算术。** `x24 = x21 + 0x2e9c51`，因此 `[x24+4] = [x21+0x2e9c55]`，**不是 c54**。原稿把 wlanUpdateNetworkAddress 的 c54 消费者当作该 6GHz 字节的消费者，相关“不是 6GHz 专用位”推论无效，撤回。同一小块的其它字段推断不能替代精确数据流。
3. 静态窗口扫描没找到直接 strb 不是证明“驱动不存在写入者”。15:18后已另由 `nicCfgChipCap6GCap` 本机反汇编和动态探针闭合来源：DisallowBand6G配置与固件支持值共同决定adapter+0x2e9c55。固件支持值实测1、原配置disallow=1；单独改为0后cap4=1并挂入6GHz表，回滚恢复0。详见运行报告第5节，不称efuse字段。
4. 运行时事实：两个周期的 `cap_read` 均返回 **cap4=0**。tracefs 七项事件和任务独立实例已正常注销，系统原有探针保留；扫描设置已恢复1。

## 1. `wlanProbe+0x5b0`：`x24` 从哪来，`[x24+4]` 是什么

### 1.1 符号定位

```
0000000000149b00 0000000000000764 t wlanProbe     # 0x149b00 .. 0x14a264
```

`wlanProbe + 0x5b0 = 0x14a0b0`，正是任务给的 kprobe 偏移；该地址落在一条指令的起始边界上（4 字节对齐），是一条**纯读**指令：

```
  14a0b0:  ldrb  w10, [x24, #0x4]
```

### 1.2 `x24` 的赋值链（逐条）

```
  149c00:  bl    wlanNetCreate                     # 返回对象 A（prGlueInfo 候选）
  149c04:  cbz   x0, ...                           # A==NULL → 错误路径
  149c08:  ldr   x8,  [x0]                         # x8 = A[0]
  149c0c:  mov   x20, x0
  149c14:  ldr   x19, [x8, #0x680]                 # x19 = net_device->priv（A 的私有区）
  149c24:  ldr   x8,  [x19]                        # x19[0] 也是 net_device*
  149c28:  str   x8,  gPrDev                       # ⇒ A[0]/x19[0] 语义 = gPrDev(net_device*)
  149c2c:  ldr   x21, [x19, x24]                   # x24 = 0x5c1a60  → x21 = *(x19 + 0x5c1a60)
  ...
  14a01c:  add   x9,  x21, #0x2e9, lsl #12         # x9 = x21 + 0x2e9000
  14a028:  add   x24, x9,  #0xc51                  # x24 = x21 + 0x2e9c51
```

`0x5c1a60` 的构造在 0x149c1c/0x149c20（`mov w24,#0x1a60` + `movk w24,#0x5c,lsl#16`）。

所以：

```
x24 = *(netdev_priv + 0x5c1a60) + 0x2e9c51
```

`x21` 是运行期从堆对象里取出的指针（不是全局），因此 `+0x2e9c51` 只是**编译期结构体偏移**，符号表里必然没有名字——这一点已由“全表无对应符号 + 该处无重定位项”双向确认。

### 1.3 `[x24+4]` 在 wlanProbe 里到底干什么

同一段代码把 `[x24+0]` 和 `[x24+4]` 分别当作 5GHz / 6GHz 的“band 是否注册”开关，写进 wdev/wiphy 的 band 指针表：

```
# --- [x24+0] → 5GHz ---
  14a054:  ldrb  w8,  [x24]                        # byte0
  14a058:  ldr   x9,  [x20]                        # x9 = wdev/wiphy 基址
  14a05c:  adrp  x10, mtk_band_5ghz
  14a060:  add   x10, x10, #0x0                    # R_AARCH64_ADD_ABS_LO12_NC mtk_band_5ghz
  14a064:  cmp   w8,  #0x0
  14a068:  csel  x8,  xzr, x10, eq                 # byte0==0 → NULL，否则 &mtk_band_5ghz
  14a06c:  str   x8,  [x9, #0x148]

# --- [x24+4] → 6GHz（wlanProbe+0x5b0 起）---
  14a0b0:  ldrb  w10, [x24, #0x4]                  # byte4  ← 唯一读取点
  14a0b4:  ldr   x11, [x20]
  14a0bc:  adrp  x10, mtk_band_6ghz
  14a0c0:  add   x10, x10, #0x0                    # R_AARCH64_ADD_ABS_LO12_NC mtk_band_6ghz
  14a0c4:  csel  x12, xzr, x10, eq                 # byte4==0 → NULL，否则 &mtk_band_6ghz
  14a0c8:  str   x12, [x11, #0x158]

# --- 同一 byte4 再判两次，作用于 P2P role wdev ---
  14a0d4:  ldrb  w11, [x24, #0x4]
  14a0e4:  str   x11, [x8, #0x158]                 # gprP2pRoleWdev
  14a0f0:  ldrb  w9,  [x24, #0x4]
  14a100:  str   x9,  [x8, #0x158]                 # gprP2pRoleWdev+0x8
```

要点：

- `[x24+4]` 在整个 `wlanProbe` 中**只被读、从不被写**；它在函数内的语义就是“6GHz band 使能位”。
- 因此若要让 6GHz band 出现，写这个字节即可（原型思路方向正确）；但**这个字节并不是 efuse 字段**，见下。

### 1.4 这个字段有没有符号 / 赋值来源

- **符号：没有。** `llvm-nm` 全表 9314 条，没有任何符号落在 `+0x2e9c51` 这一偏移上；它是结构体内偏移，不产生符号，也没有重定位项可追。
- **写入点：本 `.ko` 的 `.text` 内未找到。** 对全部 73 处 `add xN, xM, #0x2e9, lsl #12` 做窗口扫描（后续 5 条指令），没有任何 `strb` 落在 `#0xc50..0xc57`；仅有两条无关命中（`e4b54`、`145d8c`，写的是各自基址的 `#0xcf` / `#0x8a`）。
  → **该字节的填充路径未知**：可能来自运行时 memcpy/memset、芯片信息表、或其它模块（都不是本次只读静态分析能证实的）。
- **不能称为 efuse 事实。** 唯一可说的旁证是“同一 6 字节块里其它字节被 EEPROM/天线相关代码读取”，属**推测**，见 1.5。

### 1.5 同一块 `+0x2e9c51..56` 的其它消费者（同基址 0x2e9000，全部实测）

| 偏移 | 读取函数 | 语义线索 |
|---|---|---|
| `+0xc51` | `wlanProbe`、`aisFsmSteps`、`rlmDomainGetChnlList`、`rlmDomainIsLegalChannel`、`p2pRoleFsmRunEventAcs`、`glSetupP2P`、`nanCancelSubscribeRequest` | 5GHz band 使能 / 频段合法性判断 |
| `+0xc52` | `wlanoidQueryEepromType`（0x375a8） | EEPROM 类型 |
| `+0xc54` | `wlanProbe`（6GHz 门禁）、`wlanUpdateNetworkAddress`（0x98f4） | 6GHz 使能 / 另有一处用途 |
| `+0xc55` | `wlanServiceInit`（0x145d90） | 非 0 时把 `glue+0x8a` 置 1（某个能力标志） |
| `+0xc56` | `wlanoidQueryAntennaSwap`、`HQA_GetAntSwapCapability`、`hqa_get_capability`、`ServiceWlanOid` | 天线交换能力 |

> **推断（非事实）**：`eeprom type + antenna swap + band 使能` 集中在同一小块，形态很像“芯片能力/EEPROM 派生信息”结构。但本 `.ko` 内没有写入点，**不能据此把它定性为 efuse 字段**，也不能据此推断改动会被写回或持久化。

另注：`+0xc54` 同时被 `wlanUpdateNetworkAddress` 读取，说明它**不是 6GHz 专用位**，只是在 `wlanProbe` 这一处被当作 6GHz 门禁使用。

## 2. `wlanProbe` 的调用者：PCI `.probe` 是包装器

### 2.1 全 `.text` 没有一处直接调用

```
grep 'bl 0x149b00' 全 704966 行反汇编 → 0 命中
```

即 `wlanProbe` **不可能被本驱动其它函数直接调用**，只能是“取地址 + 函数指针”模式。

### 2.2 地址被取用（重定位证据）

```
# .rela.text
0000000000148ef8  R_AARCH64_ADR_PREL_PG_HI21  .text + 149b00   # adrp x0
0000000000148efc  R_AARCH64_ADD_ABS_LO12_NC   .text + 149b00   # add  x0  → x0 = &wlanProbe
0000000000148f00  R_AARCH64_ADR_PREL_PG_HI21  .text + 14a268   # adrp x1
0000000000148f04  R_AARCH64_ADD_ABS_LO12_NC   .text + 14a268   # add  x1  → x1 = &wlanRemove
0000000000148f08  R_AARCH64_CALL26            glRegisterBus

# 另有 1 处数据表类相对引用（未展开）
00000000000294e8  R_AARCH64_PREL32            .text + 149b00
```

对应 `init_module` 尾部（0x148ef0 起）实际就是：

```
init_module:
  ...
  148ef8:  adrp x0, &wlanProbe
  148efc:  add  x0, x0, #0
  148f00:  adrp x1, &wlanRemove
  148f04:  add  x1, x1, #0
  148f08:  bl   glRegisterBus
```

### 2.3 `glRegisterBus` 把两者装进总线层

`glRegisterBus`（`T`，0x23d8ac，size 0x114）内：

```
000000000023d8bc  R_AARCH64_ADR_PREL_PG_HI21   .bss + 4ddb28   # pfWlanProbe
000000000023d8c8  R_AARCH64_LDST64_ABS_LO12_NC .bss + 4ddb28   # 64 位存取 → pfWlanProbe = x0
000000000023d8d0  R_AARCH64_ADR_PREL_PG_HI21   .text + 23d9c4   # &mtk_pci_probe
000000000023d8d4  R_AARCH64_ADD_ABS_LO12_NC    .text + 23d9c4
```

符号侧对应：

```
00000000004ddb28  8  b  pfWlanProbe      # 函数指针槽（.bss）
00000000004ddb20  8  b  (邻近槽位，64 位存取于 0x23d810/0x23d814)
00000000004ddb38  1  b  g_fgDriverProbed # 单实例标志
000000000023d9c4  0x35c  t  mtk_pci_probe
```

### 2.4 `mtk_pci_probe` 是包装器，经 `pfWlanProbe` 间接进入

`mtk_pci_probe`（0x23d9c4，size 0x35c）前半段全是 PCI 资源准备：

```
pcim_enable_device → pcim_iomap_regions ×6 → pci_set_master → mtk_pcie_setup_msi → dma_set_mask
```

尾段才是进入驱动主体：

```
  23dc50:  adrp  x8, pfWlanProbe          # R_AARCH64_ADR_PREL_PG_HI21 .bss+0x4ddb28
  23dc54:  ldr   x8, [x8]                 # x8 = pfWlanProbe
  23dc58:  ldr   x1, [x21, #0x18]
  23dc5c:  ldur  w16, [x8, #-0x4]         # kCFI 类型校验
  23dc60:  movk  w17, #0xf500
  23dc64:  movk  w17, #0x6f19, lsl #16    # w17 = 0x6f19f500
  23dc68:  cmp   w16, w17
  23dc6c:  b.eq  0x23dc74                 # 通过校验 → 间接调用 pfWlanProbe
  23dc70:  brk   #0x8228                  # kCFI 失配
```

**结论（问题 2）**：PCI 侧 `.probe` 是 `mtk_pci_probe`（包装器）；`wlanProbe` 是它的被调实体，且**只能经 `pfWlanProbe` 间接进入**。除 `init_module → glRegisterBus` 外，本驱动内没有任何函数直接调用 `wlanProbe`。

## 3. 原厂注册 / 注销路径是否可“正常重入”

### 3.1 注册（一次性）

```
module_init
  └─ init_module
       └─ glRegisterBus(&wlanProbe, &wlanRemove)     # x0=wlanProbe, x1=wlanRemove
            ├─ pfWlanProbe  (.bss+0x4ddb28) = &wlanProbe
            ├─ 邻近槽位     (.bss+0x4ddb20) 收下 &wlanRemove（写入点 0x23d810/14 在紧邻的
            │                 前置胶水函数内，归属未逐条确认）
            └─ pci_driver 描述里放 &mtk_pci_probe（.text+23d9c4）
```

### 3.2 注销

- `wlanRemove`（`t`，0x14a268，size 0x5a0）是配套的 remove 实体，由同一处 `glRegisterBus` 收下。
- 模块级卸载走 `cleanup_module`（`T`，0x149060）。

### 3.3 能不能“重入”

| 维度 | 事实 |
|---|---|
| 符号可见性 | `wlanProbe` / `wlanRemove` 都是**本地符号**（`t`），不导出，其它模块无法解析调用 |
| 直接调用 | `.text` 内 0 处 `bl`，本驱动自身也不重入 |
| 入口闸门 | `wlanProbe` 第一件事就是检查 `g_wlanProbing`（`.bss` 0x42b2e8）：非 0 即**直接返回 0** |
| 官方重注册 API | 未见。唯一入口是 PCI probe → `pfWlanProbe` |

闸门代码：

```
  149b24:  adrp  x25, g_wlanProbing
  149b34:  ldr   w8, [x25]
  149b3c:  cbz   w8, 0x149b54            # 0 → 正常继续
  ...
  149b4c:  mov   w23, wzr                # 已 probing：返回值 0（成功！）
  149b50:  b     0x149f8c                # 直接走函数出口，不建 netdev
  149b54:  ...
  149b58:  mov   w8, #0x1
  149b60:  str   w8, [x25]               # 置 1
```

清零只有一处，在公共出口：

```
  149f70:  mov   x0, x19
  149f74:  mov   w1, w23
  149f78:  mov   w2, #0x1
  149f7c:  bl    glReseProbeRemoveDone
  149f80:  dmb   ish
  149f84:  str   wzr, [x25]              # g_wlanProbing = 0
```

**结论（问题 3）**：原厂有完整但**一次性**的注册/注销配对（`init_module`/`cleanup_module` + `glRegisterBus`/`wlanRemove`）；不存在可“正常重入”的对外注册路径，重复进入会被 `g_wlanProbing` 静默吞掉。

## 4. 为什么 unbind 后 bind 可能不进 `wlanProbe`

按证据强度排列：

### 4.1 已证实：`g_wlanProbing` 残留 → 静默 `return 0`

`g_wlanProbing` 是 `.bss` 里的普通 int，只在 0x149f84（公共出口）清零。只要有一次 probe 没走到该出口（例如中途异常、被强杀、或在 0x149f70 之前崩溃），它就永久停在 1，之后每次 bind 都会在 0x149b4c 返回 **0（成功）**，既不创建 netdev，也不打印错误（除非 `aucDebugModule` bit0 打开）。这正好产生“bind 看起来成功、但 wifi 没起来/没有 wlanProbe 行为”的现象。

### 4.2 已证实：入口是 `.bss` 函数指针，不是符号直接调用

`mtk_pci_probe` 在 0x23dc50 从 `.bss:pfWlanProbe` 取值，kCFI 校验后间接调用。因此：

- `glRegisterBus` 没跑过（模块加载顺序/初始化失败）→ `pfWlanProbe == NULL` → 走不到 `wlanProbe`；
- 任何清空/覆盖该槽位的路径都会让后续 bind 无法进入。

### 4.3 未验证：`g_fgDriverProbed` 与内核侧状态

- `g_fgDriverProbed`（`.bss` 0x4ddb38，1 字节）在总线胶水层（0x23d800/0x23d804、0x23d864）被读写，疑似“单实例已 probe”标志，**具体分支未逐条展开**。
- 内核侧（设备是否真的解绑、`driver_override`、module refcount、`pci_driver` 是否仍在 `pci_bus_type` 上）不在这份 `.ko` 里，**未知**。

## 5. 最小“只观察”探针建议

**位置：`wlanProbe+0x5b0`（= 0x14a0b0），kprobe pre_handler，只读不写。**

理由（全部有证据）：

1. 0x14a0b0 是 4 字节对齐的指令起点，内容是 `ldrb w10, [x24, #0x4]`——纯读，无副作用；
2. 该处 `x24` 已经算好（0x14a028 赋值），是“能力块基址 + 0x2e9c51”；
3. 6GHz 决策就在紧随的 `csel`（0x14a0c4）发生，观测点紧贴决策、无中间改写；
4. 本函数内该字节**只读不写**，观察不会改变驱动行为。

建议只记录三项（用 `probe_kernel_read` / `copy_from_kernel_nofault` 读，绝不写 `regs`）：

```
x24 的值
*(u8 *)(x24 + 0)   // 5GHz 门禁
*(u8 *)(x24 + 4)   // 6GHz 门禁（本问题核心）
```

配套再各挂一个**只记录**的 kprobe：`wlanProbe` 入口（看是否被调用、`g_wlanProbing` 的值）与 `mtk_pci_probe+0x28c`（0x23dc50，看 `pfWlanProbe` 是否为 NULL），即可把“bind 没进 wlanProbe”和“进了但 byte4=0”两类现象区分开。

> 不提供任何“写某个 cap 地址”的建议：本报告未找到该字节的写入点，写地址无证据支撑。
