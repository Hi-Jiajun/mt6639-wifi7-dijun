## 私有工作目录权限修复（原 PR #1 迭代 `v0.3.3-dijun.1`）

设备新证据定位到已匹配内核/驱动之后的初始化失败：`run-wlan-persistent` 和 `recover` 都返回 `64`、无原生日志或 guardian。安装的原生执行器哈希等于已固定原版，原生 `inspect` 成功。目录元数据显示 `/data/adb/mt6639-6g` 是 root 所有但权限为 `0777`；事务目录为 `0700`，`/odm/firmware` 为 root 所有的 `0755`。原生 `directory()` 拒绝可由 group/other 写入的祖先目录，因此在 setup 阶段失败，尚未进入该调用的原生挂载/无线动作。

共享 lib 原实现只有 `mkdir -p`，既不限制创建时的 umask，也不修正现有目录权限。无法单凭当前元数据确认是谁或哪个历史入口将目录设成了 `0777`，但模块未建立和维护原生程序要求的目录条件是已确认的软件缺口。

本批只改共享初始化：写日志/锁/状态前，以局部 umask 077 创建工作目录，核对 root 所有权，执行并核对该目录（以及已存在的 `$WORK/transactions`）为 `0700`；拒绝符号链接、非目录、外来所有者、chmod 或 stat 失败。原生执行器和目录检查不改，不递归修改子项，也不删除事务。测试模式只允许宿主夹具所有者，生产模式始终要求 root。

已有失败事务使用原有跨启动归档流程，所以**更新后需要重启**。该流程核对两份挂载空间无目标覆盖以及原厂组件/配置后才归档旧 authority，保留原事务和日志；同一 boot 下 rc64/空日志不作为无副作用收据，不自动清空。

离线验证：PR #1 原新增 7 项覆盖零 umask、新建/现有 `0777` 目录、非递归修正、符号链接/普通文件/所有者拒绝、chmod 失败、旧失败记录跨启动归档；主仓追加 1 项验证 `$WORK/transactions` `0777` 非递归收敛与符号链接拒绝。原生层用主机 C 编译器编译从生产源码提取且未修改的 `directory()`/`private_dir()`，在临时 chroot 的普通目录内复现 `0777` 拒绝、共享入口修正后通过；这不是 Android ARM64 原生程序或真实 SELinux/挂载/无线行为验证。生产模式的既有 root 身份夹具同时模拟 `$WORK` 及 `$WORK/*` 的 stat 所有者以支持非 root CI；实际权限变化和新原生祖先测试不靠该替身。

不重跑已完成的驱动二进制比较。当前硬件无线结果仍待实机验收；本修改只解决当前证据对应的原生初始化阻断（原 PR #1 社区迭代 `v0.3.3-dijun.1` 已合并为主仓 `v0.3.0`）。

## 历史迭代：驱动变体适配（原 PR #1 迭代 `v0.3.2-dijun.1`）

外部反馈证据确认：内核已匹配 `os4-stable`；两个 WLAN 驱动路径均可读取且 SHA-256 都为 `1f962c076c38c1a9e24ab7127427a1835d860aed6cb1d051a8e07b068771ac96`。此前收录的是 `1822e0f1…b5f8c342`，所以启用在身份检查阶段被拒绝，不能归因于路径或无线芯片不支持。

导出的驱动和 `wifi.cfg` 仅在主机离线只读分析：配置 SHA-256 为原有 `e4dcd846…3cc154`，逐字节相同。新旧 stable 驱动均为 8602552 字节；`.text` 的 2765664 字节完全相同。文件整体有 148322 个字节差异，涉及 `.rodata`、若干 RELA 重定位表、`.symtab` 和构建标识，不能称整个驱动完全相同。

对配置初始化/解析/读取、6GHz 能力、probe/remove、启停、请求固件和合法信道检查等 16 个函数，完整指令及规范化重定位引用比较一致；包含此前只比较指令的 `wlanInitFeatureOptionImpl` 与 `wlanLoadDefaultCustomerSetting`。比较解析 ELF64 符号表、节和 RELA，将 `.rodata` 节符号加数解析到字符串后比较。派生摘要见 [驱动比较记录](mt6639-device-driver-compat.json)。没有推断确切系统版本，没有执行新驱动或证明全部只读数据等价。

生产修改：

- 兼容表同一内核/配置行支持多个已核对驱动哈希。共享选择器读取实际驱动哈希，选定精确值；原厂身份检查、备份、恢复和状态展示继续使用这个值。
- 旧 stable 及 initial 组合保留；未知哈希、跨内核驱动错配、配置变化、无效/重复表仍拒绝。不通过系统版本号判断，也不使用内核通配符。
- 状态卡区分驱动不可读与哈希不匹配，检查入口输出预期哈希。
- 不修改原生执行器、驱动、事务流程和配置变更内容。

验证覆盖真实 cfg/ko 字节下的生产启用→备份→恢复入口，以及两个 stable 变体的恢复后检查；挂载、无线和原生执行器仍为已有替身。原厂文件和设备日志不进入公开 Git，发布 ZIP 不包含原厂驱动。

同步修正：

- 启用、原厂备份/恢复检查与 `check.sh` 不再分别写死旧驱动哈希。
- `post-reboot-check.sh` 使用共享身份数据，避免新组合已启用却在恢复检查时错误报告旧版 ko 不匹配。

- 原 `/vendor/lib/modules/…ko` 入口不存在时，支持原厂 `/vendor_dlkm/lib/modules/…ko` 路径；现存入口哈希不匹配时不会偷偷换另一份文件。
- 兼容表与选择脚本进入模块静态校验清单；本批保持原生执行器字节不变，不加载新 ko，也不修改驱动内存或 ABI。

### 适配依据

新旧原厂样本中，以下 14 个函数的完整未重定位指令字节，以及解析后的重定位目标（函数、外部符号、引用字符串）一致：

```text
wlanCfgInit, wlanCfgParse, wlanCfgGetUint32,
wlanGetConfig, wlanGetParseConfig, nicCfgChipCap6GCap,
wlanProbe, wlanRemove, wlanFuncOn, wlanFuncOff,
wlanFuncOnImpl, wlanFuncOffImpl, kalRequestFirmware,
rlmDomainIsLegalChannel
```

另外 `wlanInitFeatureOptionImpl` 的 65048 字节和 `wlanLoadDefaultCustomerSetting` 的 244 字节指令编码一致；且后续对照确认这 16 个函数的指令与规范化重定位引用均一致。原厂配置逐字节相同。新内核来自配套原厂样本及贡献者提供的 release，而不是猜测的通配版本。

这些证据支持沿用配置覆盖及原厂开关流程，**不是整个驱动、固件、内核或实际信道行为相同的证明**。本版不更换 WLAN 驱动，原生程序使用用户空间系统调用和 Binder shell 命令；MLO/TWT 独立内核模块中的旧 ABI/偏移绑定不属于本次适配。

## 模块状态卡（原 PR #1 迭代 `v0.3.0-dijun.1`）

以基线 `v0.2.16`（公开镜像提交 `2cae3c7`）为起点重做 `module.prop`，配套真实观察与动态描述写入。

初始显示：

```text
[等待状态采集] 内核：待检查 | 事务：未知 | 6GHz：未知 | 连接：未知。
```

以下是字段示例，不是本轮实机结果：

```text
[内核不匹配] 内核：不匹配 | 驱动：不匹配或不可读 | 配置：原厂 | 事务：空闲 | 6GHz：未知 | 连接：未知 | 更新：16:00:00。
```

| 字段 | 实际来源 | 含义限制 |
| --- | --- | --- |
| 内核 | 当前 release 与生产 KERNEL_GUARD 比较 | 不等于已验证整个内核 ABI |
| 驱动 | 当前入口文件 SHA-256 与已锁定原厂哈希比较 | 区分不可读与哈希不匹配；不能据此判定芯片不支持 |
| 配置 | 原厂哈希；活动事务候选哈希、boot 与挂载核对 | 不把未知变更当成模块自己的配置 |
| 事务 | 原有 native status 的 state、active_tx、guardian 身份判断 | 看护存活不是无线业务成功 |
| 6GHz | `wlan0` managed 接口所属 PHY 的 `iw` 信道列表 | 排除 disabled；没有 `iw` 或命令失败为未知；不替代关联 |
| 连接 | `iw dev wlan0 link` 中的连接状态与频率 | 不展示 SSID/MAC，不推断吞吐、带宽或业务可用性 |
| 更新 | 最近一次采集的时间 | 管理器自身可能缓存旧描述，需要刷新列表 |

状态更新接入 `service.sh`、`control.sh` 操作结束和既有 softreboot-watch 每分钟检查周期，不新增常驻进程。只读无线命令分别设 2 秒上限，native 状态查询 3 秒；不扫描、不切网、不修改国家码、不恢复事务。原有看护本身的恢复职责保留。

命令结果和周期渲染使用独立的展示锁，操作失败事件即使遇到渲染占锁也先原子保存，后续刷新仍可读取。事件按当前 kernel boot 绑定，避免上次启动的失败误显示在新 boot；观察出错不替换启用/恢复操作的实际返回码。

## 动态描述与完整性

构建把源 `module.prop` 复制为 `module.prop.template`。模板和执行脚本受 `SHA256SUMS` 校验，动态 `module.prop` 不进入静态清单。

`verify-module.sh` 首先验证清单中的模板和静态文件，然后核对展示文件与模板的所有非 description 行。仅 description 可变化；ID、版本、作者、名称等元数据修改仍被拒绝。`post-reboot-check.sh` 使用该入口，避免状态更新使正常恢复错误地报完整性失败。

状态写入在模块目录内创建临时文件再原子替换。拒绝符号链接展示文件，不将任意日志、SSID、BSSID 或其他网络身份插入描述。不运行时重算静态校验清单。这是模块自校验机制，不是对 root 写入者的安全隔离或数字签名认证。

完整校验入口：

```sh
sh /data/adb/modules/mt6639-6g/bin/verify-module.sh /data/adb/modules/mt6639-6g
```

## 初始失败证据与原厂对比

贡献者日志的关键记录为：

```text
REJECT kernel_mismatch 6.18.21-android17-5-g284297031c53-abogki553682993-4k

```

此前生产锁定的内核是 `6.18.21-android17-5-g1d099fcb35e0-abogki538445360-4k`。原始 `require_identity()` 离线复现同样返回 3，且未到达配置/驱动哈希检查，更没有进入配置覆盖和无线重建。末尾 recovery 提示是任意非零操作退出时的通用文案，不足以证明存在活动事务。

只读比较三份原厂样本：

| 文件 | `os4-initial` 基线样本 | `os4-stable` 参考样本 | 贡献者提供 `os4-stable` 变体 |
| --- | --- | --- | --- |
| wifi.cfg 长度 | 4089 | 4089 | 4089 |
| wifi.cfg SHA-256 | `e4dcd846…3cc154` | 相同 | 相同 |
| WLAN ko 长度 | 8603176 | 8602552 | 8602552 |
| WLAN ko SHA-256 | `54619c2e…64e618ea` | `1822e0f1…b5f8c342` | `1f962c07…8771ac96` |
