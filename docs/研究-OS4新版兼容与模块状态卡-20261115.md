# OS4 新版兼容与模块状态卡

日期：2026-11-15。范围：用户提供的失败日志、现有原厂样本与离线源码行为。未操作手机或无线设置。

## 当前交付：新内核适配 v0.3.1-dijun.1

**已完成 Recovery 之外的独立 6GHz 模块源码适配与离线验证，实际无线行为尚未验证。** 上批 v0.3.0 只交付状态卡，未解决内核拒绝；本批已修正这一实现缺口。

`compatibility.conf` 保存两组已知原厂组件组合：

| 组合 | 完整内核 release | WLAN ko SHA-256 |
| --- | --- | --- |
| os4-initial | `6.18.21-android17-5-g1d099fcb35e0-abogki538445360-4k` | `54619c2e9521fc084edd4ec93282715ac10e716ad4ae0a27ec5588fb64e618ea` |
| os4-stable | `6.18.21-android17-5-g284297031c53-abogki553682993-4k` | `1822e0f1e5ea4bae7fa2810bda0d775adc640efc733a045ca68694a2b5f8c342` |

两组 wifi.cfg 均要求 SHA-256 `e4dcd846f31077864932b499d462cfd6a8ca1befc6386f502813e0ba053cc154`。组合名是组件资料标签，不是读取手机系统显示版本的门禁。系统升级后上述三项不变，模块可以继续复用，不需要按 OTA 版本复制整套实现；真正变化的内核/驱动/配置需要新的兼容依据。当前日志已证实新内核 release；当前手机的实际 cfg/ko 是否匹配，由本版运行时核实，不能预先保证。

共享 `bin/compat.sh` 只读取表格，拒绝未知内核、重复条目、无效哈希、缺失/符号链接表，不使用 shell eval。`lib.sh` 用选定组合的预期哈希执行原厂身份检查；既有活动事务的候选、备份和跨 boot 整理继续沿用原实现的核对。

本批同步修正：

- 启用、原厂备份/恢复检查与 `check.sh` 不再分别写死旧驱动哈希。
- `post-reboot-check.sh` 使用共享身份数据，避免新组合已启用却在恢复检查时错误报告旧版 ko 不匹配。
- 状态卡显示 `适配：os4-stable` 或 `os4-initial`，使用同一套预期值。
- 原 `/vendor/lib/modules/…ko` 入口不存在时，支持原厂 `/vendor_dlkm/lib/modules/…ko` 路径；现存入口哈希不匹配时不会偷偷换另一份文件。
- 兼容表与选择脚本进入模块静态校验清单；本批保持原生执行器字节不变，不加载新 ko，也不修改驱动内存或 ABI。

### 适配依据

本地新旧原厂样本中，以下 14 个函数的完整未重定位指令字节，以及解析后的重定位目标（函数、外部符号、引用字符串）一致：

```text
wlanCfgInit, wlanCfgParse, wlanCfgGetUint32,
wlanGetConfig, wlanGetParseConfig, nicCfgChipCap6GCap,
wlanProbe, wlanRemove, wlanFuncOn, wlanFuncOff,
wlanFuncOnImpl, wlanFuncOffImpl, kalRequestFirmware,
rlmDomainIsLegalChannel
```

另外 `wlanInitFeatureOptionImpl` 的 65048 字节和 `wlanLoadDefaultCustomerSetting` 的 244 字节指令编码一致；这两项未在本轮比较完整重定位目标。原厂配置逐字节相同。新内核来自配套原厂样本及用户提供的 release，而不是猜测的通配版本。

这些证据支持沿用配置覆盖及原厂开关流程，**不是整个驱动、固件、内核或实际信道行为相同的证明**。本版不更换 WLAN 驱动，原生程序使用用户空间系统调用和 Binder shell 命令；MLO/TWT 独立内核模块中的旧 ABI/偏移绑定不属于本次适配。

### 定向验证

新增 12 项适配测试，包含新旧已知组合、错配/未知驱动、未知内核、配置变更、无效/重复表、拒绝执行表内 shell、状态卡，以及生产启用→备份→恢复入口和恢复后检查。挂载/原生事务执行器/无线 I/O 使用既有替身；本地提供实际原厂样本时，直接使用真实 cfg/ko 字节计算哈希及备份校验。未运行任何手机命令。

## 上一批：状态卡 v0.3.0-dijun.1

6GHz 模块源码版本 **v0.3.0-dijun.1 / versionCode 19**，重做 `module.prop`，配套真实观察与动态描述写入。上游基线提交为 `2cae3c75f5b768dc5809c5ccaa6cc05a370d99e5`。

初始显示：

```text
[等待状态采集] 内核：待检查 | 事务：未知 | 6GHz：未知 | 连接：未知。
```

以下是字段示例，不是本轮实机结果：

```text
[内核不匹配] 内核：不匹配 | 驱动：不匹配或不可读 | 配置：原厂 | 事务：空闲 | 6GHz：未知 | 连接：未知 | 更新：16:00:00。
```

| 字段 | 实际来源 | 含义限制 |
| --- | --- | --- |
| 内核 | 当前 release 与生产 KERNEL_GUARD 比较 | 不等于已验证整个内核 ABI |
| 驱动 | 当前入口文件 SHA-256 与已锁定原厂哈希比较 | 不匹配/不可读合并展示；不能据此判定芯片不支持 |
| 配置 | 原厂哈希；活动事务候选哈希、boot 与挂载核对 | 不把未知变更当成模块自己的配置 |
| 事务 | 原有 native status 的 state、active_tx、guardian 身份判断 | 看护存活不是无线业务成功 |
| 6GHz | `wlan0` managed 接口所属 PHY 的 `iw` 信道列表 | 排除 disabled；没有 `iw` 或命令失败为未知；不替代关联 |
| 连接 | `iw dev wlan0 link` 中的连接状态与频率 | 不展示 SSID/MAC，不推断吞吐、带宽或业务可用性 |
| 更新 | 最近一次采集的时间 | 管理器自身可能缓存旧描述，需要刷新列表 |

状态更新接入 `service.sh`、`control.sh` 操作结束和既有 softreboot-watch 每分钟检查周期，不新增常驻进程。只读无线命令分别设 2 秒上限，native 状态查询 3 秒；不扫描、不切网、不修改国家码、不恢复事务。原有看护本身的恢复职责保留。

命令结果和周期渲染使用独立的展示锁，操作失败事件即使遇到渲染占锁也先原子保存，后续刷新仍可读取。事件按当前 kernel boot 绑定，避免上次启动的失败误显示在新 boot；观察出错不替换启用/恢复操作的实际返回码。

## 动态描述与完整性

构建把源 `module.prop` 复制为 `module.prop.template`。模板和执行脚本受 SHA256SUMS 校验，动态 `module.prop` 不进入静态清单。

`verify-module.sh` 首先验证清单中的模板和静态文件，然后核对展示文件与模板的所有非 description 行。仅 description 可变化；ID、版本、作者、名称等元数据修改仍被拒绝。`post-reboot-check.sh` 使用该入口，避免状态更新使正常恢复错误地报完整性失败。

状态写入在模块目录内创建临时文件再原子替换。拒绝符号链接展示文件，不将任意日志、SSID、BSSID 或其他网络身份插入描述。不运行时重算静态校验清单。这是模块自校验机制，不是对 root 写入者的安全隔离或数字签名认证。

完整校验入口：

```sh
sh /data/adb/modules/mt6639-6g/bin/verify-module.sh /data/adb/modules/mt6639-6g
```

## 初始失败证据与上一批研究

用户日志的关键记录为：

```text
REJECT kernel_mismatch 6.18.21-android17-5-g284297031c53-abogki553682993-4k
control: operation=enable failed rc=3; recovery authority retained
```

生产锁定的内核是 `6.18.21-android17-5-g1d099fcb35e0-abogki538445360-4k`。原始 `require_identity()` 离线复现同样返回 3，且未到达配置/驱动哈希检查，更没有进入配置覆盖和无线重建。末尾 recovery 提示是任意非零操作退出时的通用文案，不足以证明存在活动事务。

只读比较现有两份原厂样本：

| 文件 | 上游基线对应样本 | 本地 OS4.0.4 样本 |
| --- | --- | --- |
| wifi.cfg 长度 | 4089 | 4089 |
| wifi.cfg SHA-256 | `e4dcd846f31077864932b499d462cfd6a8ca1befc6386f502813e0ba053cc154` | 相同 |
| WLAN ko 长度 | 8603176 | 8602552 |
| WLAN ko SHA-256 | `54619c2e9521fc084edd4ec93282715ac10e716ad4ae0a27ec5588fb64e618ea` | `1822e0f1e5ea4bae7fa2810bda0d775adc640efc733a045ca68694a2b5f8c342` |

两份配置完全相同，仍有 `StaEHT 1`、`ApEHT 0`、`DisallowBand6G 1` 等。两份 WLAN ELF 中 `nicCfgChipCap6GCap` 的 192 字节/48 条未重定位指令编码相同，指令字节 SHA-256 为 `0046cd5ca6be6066e39c66367683da3c8bdaa54f5f8bcda4b700d7639897ad36`。函数地址和部分 rodata 重定位偏移变化。

**这只缩小了一个函数的比较范围。** 不能据此宣布配置读取、调用者、重定位数据、信道限制、内核 ABI 或实际无线行为兼容。当前手机的原厂 cfg/ko 未包含在提供的日志中，也不能直接将本地 OS4.0.4 样本当成当前手机文件。

本批保留原有内核/配置/驱动限制，没有简单删除它们。6GHz shell 模块与 MLO/TWT 内核观察模块也不能共用一条“内核主版本相同即兼容”的结论。

## 构建与验证

源码树不保存原生可执行文件。构建器支持通过 `MT6639_MOUNT_TXN` 引用源码树外的原生执行器，仍强制核对原有 SHA-256 `8447612d22b010bcf1333a649b58917e361cfc27b22c4b11665d27ed5102768b`。本批使用已校验的上游 v0.2.16 发布包内执行器；本轮没有重建或证明该原生程序可复现。

```sh
MT6639_MOUNT_TXN=/absolute/path/to/verified/mount-txn \
  sh tools/build_6g_module.sh /absolute/path/to/NEW-output.zip
```

离线验证：

- 新增状态面板测试 18 项通过，覆盖版本拒绝、信道禁用/观察失败、事务与真实关联的区别、当前 PHY 选择、失败事件、占锁、元数据/脚本篡改、符号链接及真实控制入口返回码。
- 全部 424 项运行：375 项通过、49 项因缺少发布构件/Android 相关依赖按原规则跳过。首次运行的 8 项错误来自 PATH 未提供 clang；使用已有 clang 后完整一轮通过，没有修改对应实现来隐藏失败。
