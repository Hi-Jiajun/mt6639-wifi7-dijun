# MT6639 HyperOS 6GHz 默认搜索与 6G 徽标

日期：2026-10-23。

## 结论

“未连接 MLD 时默认搜索不到 6GHz”已经在本轮收窄到切换后的瞬态，不能再作为当前结论。6GHz 事务生效后、仍连接原 2.4GHz `Lab` 时，framework 连续三轮扫描都返回了 6135MHz 的真实 6GHz BSS；重新冷启动 Settings 后，`LabNet-6G` 和 `Lab_6G` 也正常进入 Wi-Fi 列表。

6G 徽标原型也已显示成功。干净窗口内：

- `LabNet`：真实扫描同时包含 5GHz 和 6GHz，显示 `6G`。
- `LabNet-6G`：6135MHz，显示 `6G`。
- `Lab_6G`：6135MHz，显示 `6G`。
- `LabMLO`：当前实际只有 2.4GHz + 5GHz，保持原厂 `2.4G/5G`。
- `Lab_5G`、`LabNet-5G`：保持原厂 `5G`，没有误标 6G。

徽标外观已在第二轮修正为与原厂一致：直接复用原厂 `band_wifi_5g` / `band_wifi_24g` VectorDrawable 的边框，清空内部字形，再用原厂 `MiSansLatinVF` 的 Path 重绘标签。单频 `6G` 为 22×14dp，组合标签为 48×15dp。

这仍是 Frida 原型，不是常驻模块。滚动复用没有把 6G 泄漏到 2.4/5GHz 行；断连行使用当前扫描结果，不再继承旧 `WifiInfo`。

02:00:00:00:77:7c  6135  Lab_6G

三轮 `LabNet-6G` RSSI 为 -41dBm；`Lab_6G` 为 -82dBm；6GHz affiliate 形式的 `LabNet` 为 -41dBm。原始输出保存在私有证据 `local/evidence/scan-diag-20261023/unconnected-round-{1,2,3}.txt`。

该结果说明 WiFiScanner 确实向 phy 请求了 6GHz 信道，且结果重新进入 ScanRequestProxy；当前不再需要用“连接一次 MLD 后才扫描”来触发。

## 6G 徽标原型

原厂列表在 `R.id.wifi_band` 中只处理：

```text
band_wifi_24g
band_wifi_5g
band_wifi_24g_connected
band_wifi_5g_connected
```

原型在设置行绑定完成后，先判断该行是否处于连接态：

- 连接行优先读取 `WifiInfo.getAffiliatedMloLinks()`，只统计 `MLO_LINK_STATE_ACTIVE` 的 link band；没有可用 MLO link 时才回退到主连接频率。
- 未连接行只读取当前 `ScanResult.getBand()`，避免断连后旧 `WifiInfo` 把先前的 6G 状态带到 5G-only 行。

标签组合按实际 band 集合生成：

```text
仅 6GHz       -> 6G
2.4 + 6GHz    -> 2.4G/6G
5 + 6GHz      -> 5G/6G
2.4 + 5+6GHz  -> 2.4G/5G/6G
```

单频徽标直接复用原厂 22×14dp `band_wifi_5g`；多频徽标复用原厂 48×15dp `band_wifi_24g`。两者先绘制原厂 VectorDrawable，再用 `PorterDuff.CLEAR` 清空内部字形，最后用 `/system/fonts/MiSansLatinVF.ttf` 通过 `Paint.getTextPath()` 重绘标签。字体固定为可变字重 `wght=425`。外框、圆角、描边、尺寸、夜间/连接态颜色和 40% alpha 均来自原厂资源。

原型同时覆盖：

- `MiuiAccessPointPreference`
- `MiuiWifiEntryPreference`
- `LongPressWifiEntryPreference`

干净窗口，`LabNet` 显示 `5G/6G`，`LabNet-6G` 和 `Lab_6G` 显示 `6G`：

两张裁片均为 81×51px。排除中央文字区域后，外框与背景的 1874 个像素在容差 3 内无差异。原厂 `5G` 与最终 `6G` 的 G 字形包围盒分别为 `(40,12)-(62,40)` 和 `(40,12)-(63,40)`，墨迹像素数分别为 299 和 290；数字位置、基线和字形高度一致，横向只差约 1px 的抗锯齿/rasterization 差异。

实测 `LabMLO` 连接后，framework 报告：

```text
MloLink 2.4GHz, id 0, MLO_LINK_STATE_ACTIVE
MloLink 5GHz,   id 1, MLO_LINK_STATE_ACTIVE
```

此时原厂 `2.4G/5G` 徽标保持不变，符合“连接行使用 ACTIVE link”的规则。`2.4G/6G` 与 `5G/6G` 的同一判断路径已实现，但本轮没有重新切换 AP 做这两个组合的真机复验。



## 失败路径

中间版本曾使用自定义 `ImageSpan` 把徽标塞进标题文本。该版本在一次 `updateConnectAnimation` 后触发 Settings 主线程 SIGSEGV；没有继续沿用。当前 ImageView 版本在干净窗口和滚动窗口中正常，但只运行了短时验证，不能据此认定长期注入稳定。

尝试用延时二次回写在 OEM 重绑后补徽标，也触发过 Settings 进程终止，因此已移除。`LabNet` 多频聚合行仍可能在后续 OEM 更新中回到原厂 `5G`；这个问题应通过常驻载体在进程早期安装 hook 解决，而不是在运行时反复抢写 View。

Frida、系统 APEX 或 Settings 进程在历史 detach/重绑测试中也出现过崩溃，因此常驻载体仍必须单独过：

- 冷启动和晚加载
- Settings 多次重启
- 进程异常退出与重新注入
- 模块禁用、卸载和回滚
- 与 KernelSU Manager 授权/越狱模式的联动

## 下一步

默认搜索、原生样式徽标、2.4/5/6GHz 组合标签和 MLO ACTIVE link 读取路径均已成立。剩余工作是把“单次 Frida 正确”变成“日用默认正确”：

1. 选择持久化载体，优先验证只 scope Settings 的 Vector/ZygiskNext 方案；若继续使用 Frida 服务，需要独立的进程监督、版本锁和崩溃回滚。
2. 实际切换 AP 验证 `2.4G/6G`、`5G/6G` 两个 MLO 组合，并区分 ACTIVE、IDLE 和仅扫描可见的候选网络。
3. 6G 放行事务与显示模块联动：CN 基线或事务恢复后，不得继续显示 6G。
4. 再做 Settings 多次冷启动、滚动复用、夜间模式、休眠唤醒和模块禁用/卸载验收。
