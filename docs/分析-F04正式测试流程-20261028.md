# F04 正式性能测试流程（2026-10-28）

`tools/f04_matrix.py` 把一个固定 AP 窗口的 TCP、UDP 测量串起来，默认只打印计划。只有 `--execute` 才通过 ADB 和 SSH 连接设备、临时关闭手机省电并产生测试流量。本次工具开发只做了离线自测，没有新增真机性能结论。

## 运行顺序与产物

默认共 14 项，纯流量时间 840 秒（14 分钟），另加链路核对、进程启动和清理时间：

1. 读手机 `iw dev wlan0 link`、`get power_save`，保存初始状态，确认 BSSID 和频点；保存手机 iperf 版本、rmem/wmem 上限。
2. 将省电设为 off 并读回。通过 `ssh root@198.51.100.60` 临时启动 `iperf3 -s -p 5201`，记录服务端版本和缓冲上限，不依赖 sudo。
3. TCP 按下行、上行交替跑 3 轮，每项 60 秒、4 流。
4. UDP 上行依次 500M、1G、1.5G、2G，下行依次 1G、2G、3G、4G；每档 60 秒、单流。下行默认 `-w 4M`。
5. 每项开始前、运行中（默认约每 5 秒加一次 ADB 调用耗时）、结束后保存链路和省电状态。任何一次不符或读回失败都中止后续项目，当前项和整个窗口标为 invalid。
6. 停止本次唯一标识的服务端；将手机省电恢复到初始值并读回。成功、失败、中断均写 `summary.json`、`summary.md`，保留每项原始 JSON、stderr、命令和链路快照。

输出目录必须是新目录，脚本拒绝覆盖旧结果。`summary.json` 在每轮结束时更新；突然断电、SIGKILL 或主机崩溃不能保证 finally 清理，最后一次检查点会保持 incomplete。不要据此目录作完整窗口结论。

## 参数与统计口径

- **60 秒**：已有 6 秒样本高于 60 秒持续吞吐，长窗口更能暴露热漂移和争用。正式参数要求 `--duration 60 --streams 4 --tcp-rounds 3`，改变其中任一项会标 `formal_parameters=false`。
- **TCP 4 流**：延续已有基线，降低单连接实现和拥塞控制对照的差异。不把这个结果称作单流能力。重传使用发送端 `end.sum_sent.retransmits`，上下行都记录。
- **UDP 单流**：iperf 的 `-b` 是每流速率；UDP 使用 `-P 1`，避免 4 流把“1G 台阶”变成总计 4G。默认 `-l 1200` 防止常见 MTU 下的 IP 分片，比较两组时必须使用相同包长；它与旧样本默认包长可能不同。
- **下行 `-w 4M`**：给接收 socket 明确的缓冲请求，检验旧下行高丢包是否受默认缓冲约束。Linux 内核可能对请求值加倍核算，4 MiB 与手机已知 8 MiB 的 rmem_max 相关；实际接受值和限制仍以本轮版本、原始 JSON 与错误为准。工具不改 sysctl，socket 设置失败则 invalid，不会静默退回默认值。这个选项同时影响 iperf 两端 socket，不等于仅改变手机 RX。参数名 `--no-scatter-buffer` 按任务约定保留，实际动作是省略 `-w 4M`，不修改 scatter/gather、驱动聚合或 offload。
- **接收吞吐**：TCP、UDP 一律读取 `end.sum_received.bits_per_second`。UDP 的 `end.sum` 在旧实测 JSON 中可能是发送速率，不能作为接收吞吐。工具还保存 `sum_sent` 速率，方便比对目标速率与实际发送速率。缺少明确收发汇总的 iperf JSON 拒绝入库。
- **区间与丢包**：TCP 每方向给出 3 轮均值、最小值、最大值和重传合计/均值/范围。UDP 默认每档一次，给出该档接收吞吐、接收端丢包数/包数、iperf 报告丢包率和 jitter。JSON 还计算按包数加权的丢包率；若 iperf 不同汇总计数时序使它与报告值稍有差别，保留两者，不改写原始证据。最小值—最大值只是样本范围，不是置信区间。

默认 UDP 丢包阈值为 1%，可用 `--loss-threshold` 设定。超过阈值只标 `quality=loss_above_threshold`，完整、链路稳定的高丢包测量本身仍是 valid。阈值是性能观察标准，不是硬件合格线，也不能单凭丢包把原因归为空口。

## 有效窗口判据

必须全程保持同一手机、位置、BSSID、主频点和 AP 配置；手机靠近AP-1，避免选网变化。脚本要求每次采样：

- `Connected to` BSSID 与 `--bssid` 一致，`freq` 与 `--frequency` 一致；断开、字段缺失、ADB 错误、超时一律无效。
- `Power save: off`，包括每项开始前和结束后。
- iperf 正常退出、JSON 完整、没有 error、接收统计时长处于目标时长的 95% 到目标时长加 15 秒范围内，汇总字段完整。

`iw link` 的速率带宽原样解析为 `rate_widths_mhz`；该字段反映速率采样，不能独立证明 AP 仍配置为 160/320 MHz。`--width` 是 AP 端窗口提供的配置锚点，工具不通过它切换 AP，也不会用单个较窄 PPDU 判整段无效。正式比较还需要 AP 端窗口在开测前后保存信道、宽度、center1、country、txpower、驱动/固件版本和关联记录，并确认窗口内没有改配置。`--ap-anchor` 填该会话证据路径或可定位记录。

运行中采样能发现持续漫游，但无法排除采样间隔内漫游后又回来的情况；最终结论必须结合 AP 关联日志。ADB 监视也有少量控制面开销，160/320 和缓冲对照必须保持相同轮询间隔。工具不会锁 BSSID、改选网策略、扫描、切 AP、改信道或改驱动。

任意轮链路不符，整个 14 项窗口标 invalid，后续立即停止，之前完成的数据只保留用于排错，所有组的 `eligible_for_conclusion=false`，不能挑选部分结果补成正式均值。退出码 0 表示窗口完成且清理读回成功；2 表示窗口无效或清理失败。清理失败不会篡改已经测完的窗口有效性，另见 `cleanup_ok=false`。

## 命令

先看计划和跑自测；两条都不连设备，dry-run 也不写文件。selftest 只在宿主临时目录写假输出，并明确禁止真实 `subprocess.run/Popen`：

```bash
cd $PWD
/usr/bin/python3 tools/f04_matrix.py --dry-run
/usr/bin/python3 tools/f04_matrix.py --selftest
```

AP 端窗口先确认 320 MHz 窗口并给出证据锚点，再由本窗口执行下列单命令。示例中的 `--ap-anchor` 应换成本轮实际 AP 记录；不能拿旧基线替代当前确认：

```bash
/usr/bin/python3 $PWD/tools/f04_matrix.py --execute --bssid 02:00:00:00:73:1c --frequency 6135 --width 320 --ap-anchor '本轮AP 端窗口记录路径或消息标识' --out $PWD/outputs/f04-matrix-320-$(date +%Y%m%d-%H%M%S)
```

160 MHz 对照由 AP 端窗口完成切换、稳定关联并确认新的 BSSID、主频点、center1 等参数。随后执行同一脚本，`--width 160`，同时把 `--bssid`、`--frequency` 与 `--ap-anchor` 改为实际读回值，使用另一个新输出目录。只改 `--width` 不会让 AP 变成 160 MHz。手机位置、发射功率、信道环境、UDP 包长、流数、时长、缓冲设置和轮询间隔都应保持一致；信道中心等无法保持的差异必须在 AP 锚点说明。

下行缓冲对照是在同一 AP 配置下重新跑完整矩阵，追加 `--no-scatter-buffer` 并使用新输出目录。工具不会复用上一个窗口的 TCP 或只重试出错 UDP 档；这样避免跨窗口拼接。建议按带缓冲—默认缓冲—带缓冲顺序交叉，观察随时间变化的争用与热漂移。

## 中止、清理与解释边界

正常 Ctrl-C 会让本轮和整段 invalid，停止唯一 token 对应的手机 iperf，再停本次服务端并恢复省电。手机进程使用 `-T` 唯一标识与 `/data/local/tmp/f04-*.pid`；服务端使用 `/tmp/f04-matrix-<唯一标识>/` 的 pid/log 文件。停止前核对 `/proc/PID/cmdline`，不会用 `pkill iperf3` 或停止原有监听者。5201 已占用时启动失败，中止测量，不接管现有服务。

工具保留本次手机 PID 文件和远端日志供审计，不做全局清理。进程已退出时 PID 文件不代表进程还活着。若发生断线、强制退出或 `cleanup_ok=false`，按 summary 中本次路径核对进程身份后回收；不要仅依据裸 PID 杀进程。省电原值在 `initial_link` 与初始命令原始输出中，恢复结果单列记录。

低吞吐、高 UDP 丢包、TCP 重传高都属于要解释的测量结果；只有预设阈值能给质量标记，不能自动推出驱动回归、空口损坏或 RX 缓冲根因。旧数据“TCP 下行 3G 左右、UDP 1G 却丢约三分之一”的矛盾，必须同时检查本轮接收吞吐、发送吞吐、缓冲对照和 AP 关联/空口计数后再归因。

既有基线见 `docs/验证-F04-6GHz-320MHz-TCP基线-20261028.md`。本工具未修改 release 验收清单，也没有替代 F04 的 160/320 成对实测与其他测量工具交叉验证。
