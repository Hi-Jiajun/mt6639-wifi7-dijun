## 结论

1. **TCP 双向正式数据可用**：下行 3.199 Gbps（3.127–3.277），上行 1.405 Gbps（1.381–1.428），14/14 轮全部 valid，整段判定 valid。
2. **UDP 上行只能测到发送端上限**：四档目标（500M/1G/1.5G/2G）全部收敛在 0.88 Gbps、丢包 ≤0.02%，瓶颈是手机单流 UDP 发送，不是空口。
3. **UDP 下行在本机不可作为链路指标**：iperf3 报 15%–87% 丢包，但手机内核 `RcvbufErrors` 同步暴涨（一次 8 秒 1G 目标：报丢 330,737 包，`RcvbufErrors` +298,473，占 90%）。这是手机用户态每包一次 syscall 读不过来导致的 socket 溢出，不是空口丢包。
4. 顺带修掉工具一个真 bug：`-w 4M` 在手机 iperf 3.6+ 上必炸（`unable to read from stream socket: Try again`），已改为 opt-in。

## UDP 下行（不可作为链路指标）

| 目标 | 实测 | iperf 报告丢包 |
| --- | --- | --- |
| 1G | 0.845 | 15.5% |
| 2G | 0.252 | 87.3% |
| 3G | 1.038 | 65.3% |
| 4G | 0.717 | 80.6% |

数字本身就是自相矛盾的（2G 只到 0.252，3G 反而 1.038），不满足"随目标单调"的物理预期。手工复现并对照手机内核计数器，一次 8 秒 / 1G 目标的窗口：

| 计数 | 增量 |
| --- | --- |
| `Udp: InDatagrams`（成功收下） | +503,608 |
| `Udp: RcvbufErrors`（socket 缓冲溢出） | **+298,473** |
| iperf 报告丢包 | 330,737 |

`RcvbufErrors` 解释了 90% 的"丢包"。手机侧 iperf3 每个 UDP 数据报一次 `read()` + 序号记录，十万级 pps 时用户态读不完，内核直接丢在接收队列。**这不是空口/AP 问题，是本机测量方法的上限。**

手工速率扫描也支持这个判断（省电 off、单流 1200B）：

| 目标 | 实测 | 丢包 |
| --- | --- | --- |
| 50M | 50.0 | 0% |
| 100M | 97.3 | 2.69% |
| 200M | 167.2 | 16.4% |
| 400M | 265 | ~31% |

丢包随 pps 单调上升、没有出现"周期性断流"（20 秒逐秒都是恒定 ~31%），符合缓冲溢出而非空口突发丢失。实际应用速率（通话、视频，<50 Mbps）不受影响。

**结论**：要测 6 GHz 下行 UDP，接收端不能是手机上的 iperf3。可行替代是把手机当发送端打有线接收端、或换用原生支持高 pps 的接收工具；在当前范围里不作为阻塞项。

## 工具修正

`tools/f04_matrix.py` 原本对 UDP 下行默认追加 `-w 4M`。手机 iperf 3.6+ 在这个组合下直接返回 `unable to read from stream socket: Try again`，`intervals` 与 `end` 全空，导致整段矩阵判 invalid（第一轮 10/14 即因此中断）。

改为 `--scatter-buffer` 显式 opt-in，默认不再追加；`--no-scatter-buffer` 保留为兼容旧命令行的空操作。`--selftest` 70 断言通过。

## 局限

- UDP 台阶每档只有一次（60 秒），不给统计区间；TCP 三轮给的是极差，不是置信区间。
- 下行 TCP 约 0.44% 重传率尚未与 AP 侧计数逐轮对齐，属观察值。
- 本工具不测 MCS/RU 使用率，不能把吞吐上限单独归因于某个 802.11 特性。
- 采样间隔内的短暂漫游不能完全排除；链路以开测前、轮询与结束后读回为证。
