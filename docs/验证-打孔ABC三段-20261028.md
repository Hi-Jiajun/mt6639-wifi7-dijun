## 手机侧解析到的通告（本次新增的协议级证据）

`iw scan` 里同一条 BSS 的 EHT Operation：

| 段 | EHT Operation Parameters | Disabled Subchannel Bitmap | Channel Width |
| --- | --- | --- | --- |
| A | `0x41` | 无该字段 | 320 MHz |
| B | `0x43` | `0x0f00` | 320 MHz |
| C | `0x43` | `0x00f0` | 320 MHz |

`0x41→0x43` 即 bit1（Disabled Subchannel Bitmap Present）置位。hostapd 的 `0x000f` 在空口编码成 `0x0f00`、`0xf000` 编码成 `0x00f0`，位序相反但两个段都正确落到"另一个 80 MHz 子信道"上，说明手机侧不是读配置回显，而是**真的解出了 AP 发来的打孔通告**。

## 一个被排除的混淆项：省电

采样开始时的第一个样本只有 0.997 Gbps，我一度怀疑是手机 Wi-Fi 省电（`iw dev wlan0 get power_save` = on）。随后在 C 段做交错对照（每次 4 流 6 秒下行）：

| 省电 | 下行（Gbps） |
| --- | --- |
| on | 2.807 |
| off | 2.348 |
| on | 2.782 |
| off | 2.846 |

两者区间完全重叠，**省电不是稳定解释**。回头看那个 0.997 样本的旁证：同一次 `ping -c 20` 出现 5% 丢包、max RTT 213 ms，而 A/B/C 其余样本全部 0% 丢包——它更可能落在 F03 已知的偶发丢包窗口里。协议上仍然固定"省电 off + 0% 丢包样本"再比较，但不再把省电当因果。

## 结论与边界

已成立：

1. AP 空口确实在通告打孔（`0x43` + 位图），且两个不同被打孔段都能被手机解出。
2. 打孔开启后下行吞吐稳定下降、上行不变，两段一致，排除了"配置扰动"。

仍未成立：

3. **逐 PPDU / 频谱层面"手机真的在被打孔子信道上解调"**。手机侧 `station dump` 在该驱动上为空，`/proc/net/wireless` 只有噪声/链路质量，debugfs 未挂载，驱动默认日志级别也不打印 `pp_bitmap`/`punctur` 类私有通路。要拿到这一层，需要 kprobe/ftrace 挂驱动 RX 路径或固件计数器，属新立项工作。
4. AP 侧 `PP submit ret=0` 不等于固件 ACK；本轮没有固件回执。

范围：单客户端、单点位（−40 dBm）、单信道 ch37、6 秒 ×3；未覆盖弱信号、多客户端、其它信道。
