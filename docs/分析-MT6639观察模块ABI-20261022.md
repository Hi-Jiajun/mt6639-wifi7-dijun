## 1. 总体结论

- **可编译（构建）：是。** 现有链路是自包含的：clang 独立 `-c` 编译 +
  手写 `.modinfo`/`vermagic`/`__versions` + 空 `.plt` 桩 + KCFI 前导字改写，
  无需内核源码树/头文件/Kbuild/Module.symvers。
- **可安全加载：不保证。** 编译成功≠可安全加载。加载安全依赖两项缺失 ABI
  数据（见 §4），且探针语义仍需运行时实测。

## 2. 现有证据（本地已核实）

### 2.1 struct module 偏移 —— BTF 直证 ✅
`vmlinux.btf`（recovery-20261022-1456，7.0MB）完整解析 147,887 个 BTF 类型：

| 成员 | BTF offset | probeshadow 常量 | 一致 |
| --- | --- | --- | --- |
| state | 0x0 | — | — |
| name | 0x18 | 0x18 | ✅ |
| init | 0x178 | 0x178 | ✅ |
| exit | 0x600 | 0x600 | ✅ |

自建 `struct mod_layout`（probeshadow_ksu331boot.c）偏移与 BTF 一致，
`.gnu.linkonce.this_module`（对齐 64）+ `.modinfo` 手写段方案成立。

### 2.2 模块装载版本数据
- `vermagic`：`6.18.21-android17-5-g1d099fcb35e0-abogki538445360-4k SMP preempt mod_unload modversions aarch64`
  （probeshadow_ksu331boot.c 内，与目标内核一致）。
- `module_layout` CRC：`0x60801db3`（wlan6g.ko `__versions` 实测）。

### 2.3 KCFI typeid 前导字（既有 ELF 实测）
提取方法成立：读 `.text` 中函数符号 `st_value-4` 处 4 字节。
`wlan6g.ko` 实测：

| 函数 | 位置 | typeid |
| --- | --- | --- |
| wlan6g_init | .text+0x4 | 0x6fbb3035（int(*)(void)） |
| wlan6g_pre | .text+0x5c | 0xc073bc77（kprobe_pre_handler_t） |

### 2.4 kprobe 布局 —— 仅有间接佐证 ⚠️
BTF 中未按名找到 `struct kprobe`（完整解析无该名，解析未中断）。
现存偏移（addr@0x28、symbol_name@0x30、pre_handler@0x40、post_handler@0x48）来自：
- probeshadow 源码 `struct kprobe_min` 布局；
- KernelSU `.bss` 扫描逻辑（kp.addr@+0x28、pre@+0x40）；
- 历史运行时注册成功记录。

⇒ BTF 无法直接佐证 kprobe 布局；如需更强直证需运行时手段（见 §5）。

### 2.5 头文件 / Kbuild / Module.symvers
工作区内**无**内核源码树、标准头文件、Kbuild/Makefile 或 Module.symvers。
构建完全走独立 clang 命令（见 build-*.py）。

## 3. 必须从手机采集的确切项

| 项 | 为什么缺 | 采集方法 |
| --- | --- | --- |
| `unregister_kprobe` 符号版本 CRC | 本地无任何 ko 的 `__versions` 含该项（wlan6g 仅有 module_layout；kernelsu/recovery 模块扫描均无） | ① 最可靠：目标内核构建树的 `Module.symvers`；② 或从设备上任意导出 `unregister_kprobe` 的模块（如某 vendor driver）拷贝其 `__versions` 解析；③ 或放弃在模块中引用该符号（见 §4 备注） |
| `void(*)(void)` KCFI typeid（cleanup/exit 用） | 本地已被改写的前导字只有 int(*)(void) 与 kprobe_pre_handler_t 两种 | ① 本地候选：`wlan_drv_gen4m_eap_6639.6g.ko`（8.6MB vendor 驱动）的 module_exit/exit 函数前导字；② 或 kernelsu ko 的 exit 函数前导字；③ 若二者均无合适签名函数，则从设备上任意含 module_exit 的 ko 拷贝离线提取 |
| （可选）结构级复核 | kprobe 布局 BTF 无直证 | 运行时观测：注册成功回读 `g_kp.addr` 是否等于 `ksym_addr` 解析值 |

## 4. 判定风险

1. 若新模块只引用 `register_kprobe`、不引用 `unregister_kprobe`，则加载路径
   只需已有数据（vermagic + module_layout CRC + 两个已知 typeid），静态 ABI
   风险最低。
2. 若实现卸载/清理：`mod->exit()` 是 KCFI 受检间接调用，必须用正确的
   `void(*)(void)` typeid，否则卸载即崩；且 `unregister_kprobe` 的 CRC
   缺失会导致 modversions 校验失败（加载被拒）。
3. wlan6g 现状：`__this_module.exit = NULL`、未注册清理探针，属观察型
   “永久模块”（`[permanent]`），不涉及上述两项；新模块若同样只进不出，
   同样可规避。

## 5. 建议下一步

1. 父线程先提取本地 vendor 驱动/kernelsu 的 exit 前导字（一个只读命令），
   确定 `void(*)(void)` typeid；
2. 无法取得时再列设备侧模块清单，拷贝含 `unregister_kprobe` 引用的 ko；
3. ABI 补齐后再谈“构建+加载”闭环。
