# 调研：MT6639 的 6GHz / Wi-Fi 7 前人方案与可复用证据

日期：2026-10-22。对象：小米 15S Pro（dijun）/ XRing O1 / MT6639 / HyperOS，手机内核 `6.18.21-android17`。
范围：公开网络与公开仓库的只读检索。未接触设备、未安装或运行任何下载代码、未改动任何既有文件或仓库源码、未推送。
方法：GitHub 一律走 `gh`（`api` / `search` / `contents`）；其它站点只读抓取。检索日期 2026-10-22，GitHub 代码搜索索引可能滞后数日。

## 0. 结论

1. **本轮检索未找到针对小米 15S Pro / dijun / XRing O1 的公开 6GHz 成功先例**。这是搜索范围内的否定结果，不等于公开互联网不存在此类工作。
2. **最有参考价值的素材是 MT6639 gen4m 源码**：`hurrhnn/rodin-oss-mt6639`（社区镜像，README 自述来源 POCO X7 Pro，提交 `53fa27c`；未证实是小米官方仓库，也未与本机 `.ko` 精确版本对齐）。其中的门禁链与本机观测一致：`DisallowBand6G` 在能力上报处把 `fgIsHwSupport6G` 压成 FALSE，6GHz 子带在域表查询时整段 `continue`，`wlanUpdateChannelTable()` 先把 6GHz 全部置 `DISABLED` 再按域表清位。这与“60 项 6GHz 频率 `disabled=0/no_ir=0`”的观测方向一致，但属于同族源码旁证，不是本机逐行对应。
3. **前人做过同一套做法，但公开记录只见失败的一侧**：`AndroPlus-org/magisk-module-wifi7` 会在启动早期绑定挂载 `wifi.cfg` 并把 `DisallowBand6G 1→0`，其 README 记录另一款 MTK 中国版机型（OPPO K15 Pro+，Dimensity 9500s / MT6991，ColorOS 16，KernelSU tmp root）替换后仍被驱动拒绝，日志 `Band[6G] is not allowed`。差别不在“真 root 与假 root”——tmp root 同样是真实 root 权限；差别在于该机型的驱动当时并未重新读取该配置。本机验证的是**正常 Wi-Fi 关开会让驱动重新读取 cfg 并重注册信道表**这条路径确实成立，这一点由 US 国家码在重建后才进入驱动域所佐证。
4. **Linux/PC 上有 MT7927 的作者真机报告**（项目自述 MT7927/MT6639，驱动 `mt7925e`）：单链路 6GHz 320MHz 可用；2.4G+6G 双链路 MLO 可用；作者报告 5G+6G 不能同时双链路，理由是两者共用 `band_idx=1`。这是该平台的作者结论，可作为 MLO 验收方法与候选组合的参考，不能当作本机射频拓扑或 STR/EMLSR 能力的硬约束。
5. **有作者报告 320MHz 下 TX 重传约 35% 并判断为固件侧问题**，另有“关掉 EHT 后上传吞吐约翻倍”的单作者对照。这与 AP 侧 retries/failed 偏高同向，但平台、方向、统计口径都不同，且**尚未在本机复现**；不能据此认定本机固件缺陷，也不能当成重复回包的原因。
6. **关于 6 个 ICMP 重复回包：没有找到任何 MT6639 或 MT7996 的公开来源**。公开 DUP 案例全部是桥接/VLAN/代理/双路径等二层重复。这个现象目前只能靠抓包定性，不能引用他人根因。

## 2. 源码线索：社区镜像中的 MT6639 gen4m 驱动

仓库：`hurrhnn/rodin-oss-mt6639`，`53fa27c58837c5110dd0f571048f9d42ff4302bc`（2026-06-16，README 注明 “MT6639 source from POCO X7 Pro”）。这是第三方镜像，导入链 `bsp-rodin-v-oss` 未独立核实，也未与本机 `wlan_drv_gen4m_eap_6639.ko` 的版本/构建配置对齐，因此下面只能作为**同族源码旁证**使用。
路径前缀下称 `driver/`：`connectivity/wlan/core/gen4m/`。

| --- | --- | --- |

| `driver/Kbuild.main:525`（MT6639 块）、`:621`（`CONFIG_MTK_WIFI_BW320`）、`:1456-1472`（`CFG_SUPPORT_WIFI_6G` 编译门） | 6G 是编译期开关，320MHz 单独开 | 本机能列出 60 项 6G，说明该构建已带 6G；运行期剩下的是上面两道门 |

**一个重要的反例**：`MotorolaMobilityLLC/vendor-mediatek-kernel_modules-connectivity-wlan-core-gen4-mt79xx`（`7f93dfc`）的同一函数 `nic/nic_cmd_event.c:3306` 直接把固件能力赋给 `fgIsHwSupport6G`，**没有** `ucDisallowBand6G` 判断；GitHub 代码搜索在该树内也搜不到 `DisallowBand6G`（2026-10-22）。
结论：**这个开关是项目/客户定制，不是 MTK 驱动家族的统一行为**。所以不能把“别人 MTK 机能开”或“别人 MTK 机开不了”直接外推到 dijun。

## 6. 关于 ICMP DUP 与 TX 重传：能说什么、不能说什么

**能说的**

- Linux/PC 相邻平台有“320MHz 重传偏高、EHT 路径吞吐偏低”的单作者报告（`#26`）；“固件侧、驱动不可修”是报告者的判断，本项目尚未验证。
- AP 侧 retries/failed 偏高与本项目观测同向，但那是 AP→STA 方向的统计；`#26` 是 STA 侧 `station dump`。两者的计数器口径不同，不能合并成一个结论。

**不能说的**

- 不能说“MT6639 有已知的 ICMP 重复缺陷”。本轮检索未找到可直接对应的 MT6639/MT7996 DUP 报告；检索到的其它 DUP 案例多属 VLAN 转发、桥接双路径、代理/双宿主等多路径场景，但那不是穷尽列表。
- 不能把 `#26` 的重传当成 DUP 的根因。重传是空口没收到 ACK 后的重发；DUP 是上层收到两份同样的 IP 包（可能是 AP 桥接、转发路径、或对端重传被两层都投递）。两者需要不同的证据。
- 不能把“320MHz 已协商”当成“链路质量合格”。本项目 assoc2 的 6 个 DUP 就是反例。

## 7. 可复用点与不兼容点

| 可复用 | 说明 |
| --- | --- |
| 临时 cfg 覆盖要在驱动有效重读之前对驱动可见 | 本机已用 post-boot bind + 正常 Wi-Fi 关开验证；不依赖早期 init 注入。AndroPlus 的 `initrc` 方案在本机 late-load 下不可用，只能作为时序要求的参照 |
| `cmd wifi force-country-code enabled US` 是标准入口 | AOSP `WifiShellCommand` 的 `force-country-code` 分支（`LineageOS/android_frameworks_opt_net_wifi@18e932a`，`service/.../WifiShellCommand.java:325-341`） |
| 用 GET_WIPHY 的“60 项 6GHz 全 `disabled=0/no_ir=0`”作为注册层验收 | 比“设置里能看见 6GHz”更硬；与 `wlanUpdateChannelTable()` 的行为一一对应 |
| 把 2.4G+6G 列为 MLO 首选验证组合 | Linux/PC 作者在该组合上有成功报告；本机射频拓扑、可用组合与 STR/EMLSR 仍需实测 |

| 不兼容 / 陷阱 | 说明 |
| --- | --- |
| 拿其它机型的 tmp-root 失败否定本机 | 软重启确实不会重建内核驱动，但本机不需要软重启；临时 root 同样是真实 root 权限，本机已用正常 Wi-Fi 关开完成重注册 |
| 只改国家码 | 过不了 `ucDisallowBand6G` 那道门；反过来，只改 `DisallowBand6G` 而不给含 6G 的域（US/AS 等）也拿不到信道 |
| Qualcomm 的 `WCNSS_qcom_cfg.ini` / `persist.vendor.wifi.*` 方案 | 与 MTK gen4m 完全无关 |
| 把 SoftAP 320MHz 结果当 STA 证据 | `akswap` 是 SoftAP；`DisallowAcs6G` 也只影响 AP 侧 ACS |
| 把“MLD/MLO 属性=1”当多链路已工作 | 还要过 `aps.c` 的 LinkID 位图、AP 的 MLO 配置、以及两端 `iw link`/`valid_links` 的实际证据 |

## 8. 建议的下一批安全实验（不改 root、不刷分区）

1. **先给 DUP 定性**：6GHz 关联后，手机 `wlan0` 与 AP 的 6GHz 数据接口同时抓 ICMP，比较同一 `id/seq` 的重复首先出现在哪一侧、payload 是否逐字节相同。注意普通 Ethernet/L3 `tcpdump` 看不到 802.11 Retry 位与 MAC 序号，因此它只能定位“重复包在哪一层已经存在”，**不能单独判定空口重传**；要判 802.11 层重试需另设 monitor/radiotap 采集。
2. **重传单变量**：另行排期并备份后，同一 AP、同一位置、320MHz 与 160MHz 各做相同时长的空闲与 `iperf3` 对照，记录 retries/failed **增量**与吞吐。160MHz 也偏高只能说明现象不局限于 320MHz，不能反过来排除 320MHz 的额外影响。本轮不改 AP 配置。
3. **MLO 门槛检查**：核对 AP 与手机双端的 MLD/link 信息，2.4G+6G 作为首选候选但非唯一允许组合。`valid_links` 有多位只表示建立了多链路，不等于同时收发或 STR 生效，收益另测。
4. **固定固件变量**：记录手机 WLAN 固件 build time 与驱动版本，与每次 retries 一起存档；相邻平台的作者报告显示换固件不必然改善，需按版本对比而非假定。
5. 以上都不需要重新打开 `DisallowBand6G` 之外的开关，也不建议在未抓到包前调 `rts/cts` 或改 AP 国家码。

## 9. 明确的证据缺口与可能的误报

- 本轮未检索到 dijun/15S Pro 的同类公开实测；**不主张首创**——搜索索引、私有社区与未索引内容都有盲区。
- `AndroPlus` 的失败是**另一台机型 + 该机驱动未重读配置**，不能证明“MTK 上这套方法不可行”，也不能反证我们的成功可以复制到别的 MTK 机型。
- `#8`/`#26` 都是单作者、Linux/PC、固件版本各异的报告；`#26` 的 35% 是“某固件、320MHz”，不是所有 MT6639。
- `akswap` 是 Qualcomm + SoftAP；`OnePlus_Beast` 是属性堆叠，均不能当作 MTK STA 的能力证据。
- “注册出 60 个 6GHz 信道”只证明驱动/域表层放行；不等于扫描、关联、数据、320MHz、MLO 都通过。
- “320MHz 协商”只证明双方 EHT 能力与当前 RF 允许；不等于吞吐、稳定性、长期可用。
- “MLD 配置存在”不等于多链路活动；需要 `valid_links`/`iw link` 的双链路证据。
