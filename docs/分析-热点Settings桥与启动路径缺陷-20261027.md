# 热点 Settings 桥：UI 能长出来，但请求到不了、启动起不来（2026-10-27）

## 结论

设置里那套 `MT6639 实验热点` 控件（标题 / 状态行 / 启动入口 / 频段带宽选择框 / 不可启动原因）**能正常渲染**，说明 LSPosed 注入与 `MiuiTetherSettings`、`AllInOneTetherSettings` 钩子都是通的。但点下去之后有两处真缺陷，当前**一次成功的 6G 热点启动都还没做成**。

## 缺陷 1：请求队列路径不一致（已修，v0.2.10）

| 侧 | 路径 |
| --- | --- |
| Settings（UI 模块） | `/data/user_de/0/com.android.settings/files/mt6639-hotspot` |
| `request_worker.sh`（v0.2.9） | `/data/user/0/com.android.settings/files/mt6639-hotspot` |

这台机器上 `/data/user/0/com.android.settings/files` **不存在**（Settings 这份系统应用用的是 device-protected 存储），所以 UI 写的请求永远落在 worker 不看的目录里。

证据：UI 提交后 `request.<nonce>.req` 出现在 `/data/user_de/0/...`，内容为
`schema=mt6639-hotspot-request-v1 / op=start / band=6g / width=20 / boot=936ecd0f…`；而 worker 侧 `bridge/last-result` 一直没有新条目。

修法：worker 依次尝试 CE、DE 两个路径，命中哪个用哪个。安全边界没变 —— 两个目录都要求 `uid/gid=1000`、`mode=700`、label `u:app_data_file`→实际为 `u:object_r:system_app_data_file:s0`，DE 那份实测 `1000 1000 700 u:object_r:system_app_data_file:s0` 完全符合。

修完立刻见效：`last-result` 出现 `result=start:6g:20 … rc=69`，说明请求确实被消费、控制器真的被调起来了。

## 缺陷 2：`control.sh` 读 `/proc/*/cmdline` 无超时（已修，v0.2.10）

`guardian_process_without_record()` 会遍历整个 `/proc/[0-9]*`，对每个 pid 执行 `tr '\000' ' ' < "$p/cmdline"`。只要有一个进程的 cmdline 读卡住，这个循环就永远不返回 —— 表现是状态永久停在 `starting`，并且它握着 `action.lock`，后续任何 start/stop 都返回 `REJECT action_busy`。

实测：`control.sh`（pid 21682）跑了 4 分钟，子进程 `tr`（pid 21799）一直挂着；`/proc/21682/fd/7 -> action.lock` 证实锁在它手里。

修法：三处 `tr` 全部改成 `timeout 2 tr …`，最坏情况也有界。

## 缺陷 3：失败诊断信息不外露（未修）

- 控制器把 runner 输出重定向到 `$task/session.log`，但那次失败时该文件是 **0 字节**，看不到原因。
- 失败后留下的 `claimed` 文件（runner 用 `set -C` noclobber 创建）会让下一次启动直接 `exit 73`，对外只表现成 `REJECT runner_exited_during_start`，容易被误判成"驱动不支持"。
- 用 `sh -x` 才能定位到是 `set -C; > $D/claimed` 这一步失败。

建议：runner 启动失败时把首行错误写进 task 目录的固定文件并让 `control.sh` 带回；`recover` 顺带清理过期的 `claimed`。

## 还有一个前置条件（不是缺陷）

6G 实验热点要求 **STA 先连在 `LabNet-6G` / 6135MHz / `02:00:00:00:73:1c`**（runner 里写死 `UPSTREAM_SSID/FREQ/BSSID`）。手机当时在 LabNet-5G 上，runner 因此提前退出。把 STA 切到 6G 后，同一条路径的失败原因就变成了上面那个 stale `claimed`。

## 当前状态（收尾后）

- 模块版本：`v0.2.10 / versionCode 18`（含上述两处修复），ZIP 已构建：`outputs/hotspot-module-20261027/mt6639-hotspot-v0.2.10.zip`，SHA256 `b7d6d637bf6a62f3e32f61af0bdd98d7179361aaaca4bec8c31300a02297d301`。

- 现场已清理：没有残留 `control.sh`/`softap_native_once` 进程、没有 `mtap0` 接口、快照已重新发布为 `state=idle`。
- 6GHz STA 仍连在 `LabNet-6G`/6135。

# 第二轮：无 Wi‑Fi 场景、cellular 上游与"起来又自拆"（v0.2.11）

## 问题：不连 Wi‑Fi 能不能开 6G 热点

拆成三层，结论不一样：

| 层 | 结论 | 证据 |
| --- | --- | --- |
| 6G AP 是否必须有一个 6G STA 在连着 | **不必须** | 见下：STA 连在 5G 时 6G AP 正常起、`freq=6135` |
| Wi‑Fi 完全关掉能否开 AP | **当前不行** | Wi‑Fi 关闭后 `iwpriv wlan0 driver 'GET_CFG ApEHT'` 返回 `wlan0 no private ioctls`，runner 在 `ap_value` 处 `exit 69`；驱动没挂上，连 `mtap0` 都建不了 |
| 上游走蜂窝 | **本次未达成** | 本轮 Tethering 选的仍是 `wlan0`（因为 Wi‑Fi 还连着）；要真正走蜂窝需要让 Tethering 选 `wwan/rmnet`，属新增工作 |

也就是说，之前那条"必须先连 `LabNet-6G`/6135"是**我们自己加的门禁**，不是硬件要求。

## 本轮代码改动（v0.2.11 / code 19）

1. `MT6639_HOTSPOT_UPSTREAM=cell` 实验模式：跳过 STA 上游门禁，并把 Tethering 断言的上游从 `[wlan0]` 放宽到 `[(rmnet|wwan|ccmni|seth|eth)…]`。`control.sh` 启动 runner 时会把这个变量显式传下去。
2. 回收残留 `claimed`：拿到 `owner.lock` 之后先 `rm -f claimed` 再创建，避免一次失败就把后续所有重试钉死在 `exit 73`。
3. `init.svc.hostapd` 属性缺失时不再当成失败（这台机器根本没有这个 init 服务），空值等同 `stopped`。
4. runner 失败原因写入 `$D/failure`，`control.sh` 在 `REJECT runner_exited_during_start` 时带上 `reason=…`；此前只能看到裸退出码，要靠 `sh -x` 才挖得出来。

## 实测：6G AP 真的起来了（Wi‑Fi 开、STA 在 5G、上游模式 cell）

```
state=active task=…-PtiVkJ pid=5211 band=6g width=20 hold=86400
iw dev mtap0 info        -> type AP, ssid MT6639-Native-6g-20, wiphy 0
hostapd_cli status       -> state=ENABLED, freq=6135
softap-profile status    -> native_status=matched band=6g frequency_mhz=6135 width_mhz=20 center_index=37
address.active           -> mtap0 inet 198.18.117.110/24
tether.active            -> mtap0 - TetheredState - lastError = 0；upstream = [wlan0]
```

关键收获：**mtap0 在 6GHz 起来的同时，STA 仍稳稳连在 5G 上**，DBDC 跨频共存没有冲突。

## 但它在一分钟内自己拆了

- `action.rc=1`、`cleanup.request` 被创建，hostapd 日志是受控关闭：`interface state ENABLED->DISABLED … AP-DISABLED … CTRL-EVENT-TERMINATING`，不是崩溃。
- 失败点在**收尾自检链**：`profile.final` 文件根本不存在、`recovery.rc` 也缺失，说明这一段
  `native_identity && hostapd_cli status && profile status > profile.final` 没走完就退出了。
- 换句话说：**AP、Tethering、IP、信道都对，挂的是"起来之后的自检"**。这条自检链本身需要单独查（`native_identity` 在 tethered 之后为何返回假、以及 `recovery.rc` 谁负责写）。
