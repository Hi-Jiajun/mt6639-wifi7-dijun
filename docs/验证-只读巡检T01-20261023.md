## 首轮现场

宿主机 Python 3 标准库入口 `tools/inspect_mt6639.py`，使用已有 root ADB 和事先核对 SHA256 的 GET_WIPHY 只读 helper。没有扫描、切换网络、修改配置、国家码或 AP 状态。

- 同一 boot，设备 Dijun、内核 `6.18.21-android17-5-g1d099fcb35e0-abogki538445360-4k`。
- cfg SHA256 为 `e4dcd846f31077864932b499d462cfd6a8ca1befc6386f502813e0ba053cc154`，`DisallowBand6G=1`。
- WLAN ko SHA256 为 `54619c2e9521fc084edd4ec93282715ac10e716ad4ae0a27ec5588fb64e618ea`。
- 当前 CN、5180MHz、COMPLETED；保存网络按不同 ID 计数为 4；KSU 3.3.1。
- 原厂当前 wiphy 注册 2.4/5GHz，没有注册 6GHz；这不是对射频硬件缺失的判断。
- `wpa_cli mlo_status` 返回 `FAIL`，采集器正确登记查询失败，不能据此判定 MLO 硬件不支持。
- SELinux 当前仍为 Permissive，本项目没有更改，也未宣称修复系统安全姿态。

45 个探针：37 个标记 ok、6 个候选 cfg 路径缺失、1 个 MLO 查询失败、1 个蓝牙服务属性为空。**其中 dumpsys 的 ok 是误报，不能按 37 项全部可信统计**：原始 stderr 为 `sh: /system/bin/printf: Argument list too long`，stdout 只有 `dumpsys_rc=0`。采集器只检查内部 dumpsys 状态，漏掉了后续过滤失败。单独只读过滤命令能取到 driver CN、override=null，因此这是采集实现缺陷，不是设备不支持该查询。

## 修复后现场复测

过滤链改为流式处理，不把完整 dumpsys 作为单个外部程序参数；同时记录 `dumpsys_rc` 与 `filter_rc`。再次运行全部只读探针，输出到新私有目录 `local/evidence/t01-live-20261023b/`，前后核对工具源文件 SHA 一致。

本轮取得 `mDriverCountryCode=CN`、`mOverrideCountryCode="null"`，两个 rc 均为 0，stderr 为空。这里字符串 `"null"` 表示确实读到“无覆盖”，不同于 JSON `null` 的“没采到值”。版本字段未出现，仍保留未知，不从“部分字段成功”推出其它字段存在。

45 个探针仍为 37 ok / 6 missing / 1 failed / 1 empty；这次 dumpsys 有实际匹配字段，ok 不再来自状态码标记一项。唯一 failed 仍是 MLO 查询的 `FAIL`，不是 MLO 不支持。设备 boot、cfg/ko hash、CN、5180MHz/COMPLETED 与保存网络 ID 数量均保持原基线；没有变更性操作。

修复代码尚待独立复审与测试结果收齐，本次现场成功不自动把 T01 全部验收条件打勾。

本窗口随后在同版代码执行完整离线测试：`python3 -m unittest discover -s tests -v`，14 项通过，103.110 秒。包含实际运行生成过滤命令、处理超过 1MiB 模拟输出的用例；宿主机 shell 与 Android 的内建命令实现不同，宿主回归不能单独证明 Android 的 ARG_MAX 路径，以上真机复测是另一个必要证据。限定范围复审仍在进行。
